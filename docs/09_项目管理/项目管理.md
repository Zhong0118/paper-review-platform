# 项目管理与阶段计划

## 1. 当前阶段

当前处于“文档补齐”阶段，尚未进入文档一致性复查、编码准入、实施计划或代码开发。本文只确定阶段、范围和管理门禁，不构成编码授权。

## 2. 阶段与出口条件

| 阶段 | 主要产物 | 出口条件 |
|---|---|---|
| 1. 资料盘点 | 来源索引、目录导航 | 原始与正式材料可追溯 |
| 2. 文档审查 | 覆盖矩阵、一致性报告 | 缺失、冲突和风险已登记 |
| 3. 问题讨论与决策 | 问题决策记录、CONTEXT | 阻塞性业务规则已有明确决定 |
| 4. 文档补齐 | 00—09 正式文档、ADR、追踪矩阵 | P0 可设计、可测试、边界明确 |
| 5. 文档一致性检查 | 更新审查报告和覆盖矩阵 | 需求—流程—API—表—测试一致 |
| 6. 编码准入审查 | 编码准入检查表 | 无未处理 P0 阻塞项 |
| 7. 实施计划编制 | 可独立验收的分阶段计划 | 用户审阅并确认计划 |
| 8. 代码开发 | 功能、迁移、测试、同步文档 | 用户明确“批准进入编码阶段”后方可开始 |
| 9. 测试验证 | 验收证据和缺陷记录 | 当前交付范围通过门禁 |
| 10. 文档同步 | 实现一致的正式文档 | 版本可交付和维护 |

## 3. 优先级定义

- P0：首发最小闭环和安全底线，缺失时不能上线。
- P1：应在后续近期版本完成的增强能力，不阻塞 P0 快速交付，但在进入对应实现前需补齐详细设计。
- P2：远期探索能力，只保留边界和方向，当前不做实现承诺。

优先级不是风险等级。需求 P0/P1/P2 表示交付顺序；审查风险 P0/P1/P2/P3 表示问题严重程度。

## 4. P0 建议实施增量

正式实施计划仍需在编码准入后单独编制。建议按以下可验收增量推进：

1. 租户、学校同步、五角色与权限隔离；
2. 学生论文草稿、文件上传、提交和匿名检查；
3. 学校材料确认、平台专家库与人工指派；
4. 专家邀请、接受/拒绝、在线评阅和最终提交；
5. 超时、催审、延期、撤回、改派和补审；
6. 汇总、冲突、发布、学生/导师查看和异议登记；
7. 费用、余额、提现申请和人工支付回填；
8. 通知、审计、导出、备份恢复和上线门禁。

每个增量都必须包含后端、前端、数据、权限、测试、运维和文档，不把安全或测试统一推迟到最后。

## 5. 范围控制

P0 不包含自动专家推荐、自动生成匿名文件、完整在线复核、自动支付、AI、深度查重、微信小程序、高级统计、微服务、Kubernetes 或多地域。发现新需求时先记录来源、用户价值、依赖、风险和建议优先级，未经确认不得插入当前增量。

不得为 P1/P2 能力预建空业务函数、无调用模块或复杂通用框架。只保留经过 ADR 确认且成本很低的稳定扩展接口。

## 6. 需求与变更管理

### 6.1 编号和追踪

使用 BR、FR、NFR、ROLE、FLOW、PAGE、API、TABLE、TC、AC、RISK、ADR 编号。P0 必须形成：

```text
BR → FR → ROLE → FLOW → PAGE → API → TABLE → TC → AC
```

### 6.2 变更流程

1. 在问题与决策记录中登记变更及来源；
2. 分析对权限、状态、数据、API、测试、安全和进度的影响；
3. 对重大技术选择新增或更新 ADR；
4. 用户确认后更新正式文档和追踪矩阵；
5. 若已进入开发，更新实施任务、测试和回滚方案；
6. 未经确认不得把推测写成已批准规则。

## 7. 文档评审与批准

- `DRAFT`：内容正在编写或尚未完成内部检查。
- `REVIEWING`：已形成完整评审稿，等待用户或相关负责人审阅。
- `APPROVED`：用户明确批准该版本。
- `DEPRECATED`：已由新版本替代并保留历史链接。

本轮新增正式文档均保持 `DRAFT`。完成一致性自查后可改为 `REVIEWING`，但不得自行改为 `APPROVED`。

## 8. 风险管理

| 编号 | 风险 | 当前控制 |
|---|---|---|
| RISK-001 | 跨学校数据泄露 | 应用过滤 + PostgreSQL RLS + 对象前缀/桶 + 越权测试 |
| RISK-002 | 作者或专家身份泄露 | 分端投影、原件/匿名件隔离、下载审计、特殊解盲流程 |
| RISK-003 | 状态与历史被覆盖 | 分层状态机、版本表、只追加事件、乐观锁 |
| RISK-004 | 重复指派、提交、通知或入账 | 幂等键、唯一约束、事务和重试设计 |
| RISK-005 | 上游学校数据不可靠或延迟 | 来源版本、同步记录、安全重放、人工告警而非本地擅改 |
| RISK-006 | 自动支付合规和资金风险 | P0 人工支付回填；P1 独立合规与供应商设计 |
| RISK-007 | 数据与文件无法一致恢复 | 每日联合备份、7 个恢复点、上线前恢复演练 |
| RISK-008 | 范围膨胀拖慢首发 | 冻结 P0，P1/P2 不预建空实现，变更走决策流程 |

## 9. 交付和验收责任

产品决策负责明确业务目标、角色、流程和优先级；架构设计负责模块、数据、安全和集成约束；开发负责按追踪项实现；测试负责独立验证正常、异常、越权和恢复；运维负责环境、发布、监控、备份与事件响应。具体人员名单和排期在团队确定后补充，不在当前文档虚构。

## 10. 紧接着的工作

完成本轮 00—09、ADR 和 P0 追踪矩阵后，应先进行文档一致性检查并更新审查报告；随后才进行编码准入审查和实施计划编制。即使准入通过，也必须等待用户明确编码授权。
