# 百杰校审平台企业级总体设计与开发文档

> 文档版本：V1.0  
> 文档类型：产品需求说明 + 技术架构设计 + 开发实施方案  
> 适用对象：产品经理、项目经理、后端工程师、前端工程师、测试工程师、运维工程师、交付团队  
> 项目定位：面向高校学位论文送审、盲审、专家评阅与结果归档的企业级管理平台

---

## 1. 项目概述

### 1.1 项目名称

**百杰校审平台**

副标题建议：

**学位论文送审平台**

完整品牌表达：

```text
百杰校审 —— 学位论文送审平台
```

### 1.2 项目定位

百杰校审平台是一套面向高校、学院、研究生管理部门、评审专家及第三方论文送审服务商的企业级论文送审管理系统。

平台围绕学位论文送审业务，覆盖论文提交、材料审核、盲审处理、专家匹配、专家接审、在线评阅、结果回收、复审处理、评阅书生成、费用结算、数据统计与流程归档等核心环节。

系统目标不是单一的论文上传工具，而是一套可长期迭代、可多学校部署、可支持多角色协同、可对接高校存量系统的综合性送审业务平台。

### 1.3 建设目标

平台建设目标包括：

1. 实现论文送审全流程线上化，减少人工沟通、Excel 流转和线下统计成本。
2. 实现学生、导师、管理员、专家等多角色协同，保证任务清晰、状态可追踪。
3. 实现专家库、论文库、评阅结果和费用结算的统一管理。
4. 实现论文材料、评阅过程、结果发布的权限控制与审计留痕。
5. 支持多个学校、多个学院、多个批次、不同评审规则的配置化管理。
6. 支持后续扩展专家智能匹配、匿名化检测、格式检测、AI 评语检查、统一身份认证对接等能力。
7. 支持中小企业级交付，兼顾快速开发、低耦合架构和后续服务化演进。

### 1.4 业务核心价值

平台核心价值体现在以下方面：

| 价值方向 | 说明 |
|---|---|
| 流程提效 | 将论文提交、审核、送审、评阅、结果归档统一线上化 |
| 降低人工成本 | 减少人工派单、人工催审、人工汇总、人工导出 |
| 保障盲审公正 | 支持匿名化、专家回避、权限隔离、审计留痕 |
| 专家资源沉淀 | 建立可复用专家库，记录专家领域、评审周期和质量 |
| 多校复用 | 支持多学校、多学院、多批次、多模板配置 |
| 商业化支撑 | 支持中间商平台承接送审服务、管理专家和结算费用 |
| 后续智能化 | 为专家匹配、论文检测、AI 辅助评审预留技术接口 |

## 2. 设计原则

### 2.1 第一性原则

论文送审平台的本质不是“上传文件”，而是解决以下几类问题：

1. **流程问题**：论文从学生提交到最终归档存在多个审核、评阅和结果判定节点。
2. **权限问题**：不同角色只能看到自己有权查看的数据和材料。
3. **公正问题**：盲审要求专家、学生、导师之间信息隔离，避免利益关系影响评审结果。
4. **效率问题**：批量论文、批量专家、批量通知、批量导出必须自动化。
5. **安全问题**：论文文件、专家意见、评审结果均属于敏感数据，必须控制访问和下载。
6. **扩展问题**：不同学校规则不同，系统不能写死流程、模板和权限。
7. **商业问题**：平台需要支撑第三方服务商进行多校、多批次、多专家资源管理。

### 2.2 架构设计原则

系统采用以下设计原则：

```text
模块化单体优先
领域边界清晰
权限模型统一
流程状态集中管理
文件存储统一管理
通知能力统一封装
外部对接适配化
后期可拆微服务
```

### 2.3 不采用早期微服务的原因

项目第一阶段不建议直接采用微服务架构。原因如下：

1. 早期业务边界尚未完全稳定，过早拆分会增加通信和联调成本。
2. 论文、审核、送审、评阅、结果之间事务关系较紧，早期拆服务会增加一致性复杂度。
3. 微服务会引入注册中心、网关、链路追踪、服务鉴权、分布式事务、日志聚合等额外成本。
4. 当前更重要的是快速实现可交付业务闭环，而不是过度工程化。

正确方式是：

> 按微服务边界设计模块，但以模块化单体方式开发和部署。

## 3. 总体技术选型

### 3.1 推荐技术栈

| 层级 | 推荐方案 | 说明 |
|---|---|---|
| 前端框架 | Vue 3 + TypeScript + Vite | 适合管理后台、表格表单、快速开发 |
| UI 组件库 | Element Plus | 国内管理系统成熟、组件丰富 |
| 状态管理 | Pinia | Vue 3 官方推荐生态 |
| 路由 | Vue Router | 前端路由管理 |
| 图表 | ECharts | 数据统计和看板展示 |
| PDF 预览 | PDF.js | 专家端在线查看论文 |
| 后端框架 | FastAPI | 开发效率高，适合业务 API、文件、AI/PDF 扩展 |
| ORM | SQLAlchemy 2.x | Python 生态成熟 ORM |
| 数据迁移 | Alembic | 管理数据库版本 |
| 数据库 | PostgreSQL 或 MySQL 8 | 业务主库，国内交付可优先 MySQL |
| 缓存 | Redis | Token、验证码、任务状态、热点数据缓存 |
| 文件存储 | MinIO | 私有化对象存储，兼容 S3 协议 |
| 异步任务 | Celery | 批量导入、导出、通知、PDF 处理 |
| 消息队列 | Redis / RabbitMQ | MVP 可用 Redis，正式环境建议 RabbitMQ |
| 定时任务 | Celery Beat / APScheduler | 催审、超时扫描、报表生成 |
| 网关 | Nginx | HTTPS、反向代理、静态资源服务 |
| 容器化 | Docker / Docker Compose | 中小规模部署简单可靠 |
| 可选 Java 服务 | Spring Boot Adapter | 对接学校老 Java 系统、CAS、jar SDK、SOAP |
| 日志 | structlog / loguru + 文件/ELK 可选 | 结构化日志 |
| 测试 | pytest | 后端自动化测试 |

### 3.2 FastAPI 与 Spring Boot 的边界

主业务系统推荐采用 FastAPI，原因如下：

1. 业务早期变化快，FastAPI 开发效率更高。
2. PDF、Word、Excel、AI 检测、匿名化分析等能力在 Python 生态中更自然。
3. 小团队更容易快速交付 MVP。
4. 可以通过严格模块化、类型约束和测试规范控制工程质量。

Spring Boot 不作为主业务系统的原因：

1. 项目初期会显著增加代码量和工程复杂度。
2. 对快速迭代不如 FastAPI 友好。
3. PDF/AI/Excel 处理最终仍然大概率要调用 Python 服务。

但保留 Java Adapter 的原因：

1. 高校存量系统大量为 Java 项目。
2. 某些学校可能只提供 Java SDK、jar 包或老式 WebService。
3. CAS、LDAP、SAML、特殊加密签名等场景，Java 生态更容易适配部分老系统。

因此最终推荐架构是：

```text
FastAPI 主业务系统 + 可选 Java Adapter 对接服务
```

## 4. 系统总体架构

### 4.1 架构总览

```text
用户端
├── 学生端 Web/H5
├── 导师端 Web

└── 管理后台 Web

        ↓

前端层
Vue 3 + TypeScript + Element Plus

        ↓

接入层
Nginx / HTTPS / 反向代理 / 静态资源

        ↓

应用层
FastAPI 模块化单体
├── auth        认证登录
├── tenant      学校与租户
├── user        用户权限
├── thesis      论文管理
├── workflow    流程审核
├── expert      专家库
├── dispatch    送审派单
├── review      专家评阅
├── result      结果管理
├── notice      通知催审
├── finance     费用结算
├── statistics  统计分析
├── file        文件存储
├── template    模板配置
├── audit       审计日志
└── integration 外部对接

        ↓

基础设施层
├── PostgreSQL / MySQL
├── Redis
├── MinIO
├── Celery Worker
├── RabbitMQ / Redis Queue
└── Java Adapter 可选

        ↓

外部系统
├── 学校统一认证
├── 研究生管理系统
├── 短信平台
├── 邮件服务
├── 查重系统
├── 支付/结算系统
└── 云服务/对象存储
```

### 4.2 模块化单体说明

系统在代码层面按业务领域拆分模块，每个模块拥有自己的接口层、业务层、数据访问层、数据模型、权限校验和事件定义。

部署层面第一阶段保持一个主应用，避免微服务带来的复杂度。

后期可优先拆分以下服务：

| 可拆服务 | 拆分原因 |
|---|---|
| 文件服务 | 文件上传下载流量较大，安全要求高 |
| 通知服务 | 短信、邮件、微信通知异步且可独立重试 |
| PDF/AI 检测服务 | 计算密集型任务，需要独立扩容 |
| 外部对接服务 | 各学校对接差异大，可独立维护 |
| 统计分析服务 | 数据量大后可独立做聚合和缓存 |
| 专家匹配服务 | 后期算法化后可独立演进 |

## 5. 用户角色与权限设计

### 5.1 角色设计原则

系统不应一开始设计过多固定角色，而应采用：

```text
少量基础角色 + 细粒度权限点 + 独立数据范围 + 一人多角色
```

角色不是现实身份的完全映射，而是权限集合。现实中的研究生院管理员、学院秘书、财务人员、学科秘书等，可以通过权限和数据范围组合实现。

### 5.2 第一版核心角色

| 角色 | 说明 | 核心功能 |
|---|---|---|
| 学生 | 论文提交者 | 填写论文信息、上传论文、查看状态、下载结果 |
| 导师 | 学生论文初审人员 | 查看学生论文、审核、驳回、查看结果 |
| 业务管理员 | 学院/学校/中间商运营人员 | 审核、送审、指派专家、催审、导出结果 |
| 专家 | 论文评阅人员 | 接收任务、查看论文、填写评阅书、提交评审 |
| 平台管理员 | 系统配置和平台维护人员 | 管理学校、用户、模板、规则、权限、日志 |

### 5.3 后期可扩展角色

| 角色 | 说明 | 是否第一版需要 |
|---|---|---|
| 研究生院管理员 | 全校送审业务管理 | 可由业务管理员 + 全校数据范围实现 |
| 财务人员 | 专家费用结算与导出 | 可后期增加 |
| 审计员 | 只读查看日志与流程记录 | 后期增加 |
| 运维管理员 | 系统运行维护 | 后期增加 |
| 学科秘书 | 学位点或专业维度管理 | 可由业务管理员配置数据范围 |
| 分委员会管理员 | 特定评审委员会管理 | 后期按需求增加 |

### 5.4 权限模型

采用：

```text
RBAC + 数据权限 + 操作权限
```

#### 5.4.1 RBAC 模型

核心对象：

```text
用户 User
角色 Role
权限 Permission
菜单 Menu
用户角色 UserRole
角色权限 RolePermission
角色菜单 RoleMenu
```

#### 5.4.2 操作权限

典型权限点：

```text
thesis:create        创建论文
thesis:upload        上传论文
thesis:view          查看论文
thesis:update        修改论文
thesis:delete        删除论文
thesis:audit         审核论文
thesis:dispatch      送审论文
expert:create        新增专家
expert:import        导入专家
expert:view          查看专家
review:submit        提交评阅
result:view          查看结果
result:publish       发布结果
result:export        导出结果
finance:view         查看费用
finance:export       导出结算
system:config        系统配置
log:view             查看日志
```

#### 5.4.3 数据权限

| 数据范围 | 说明 |
|---|---|
| 本人 | 学生只能看自己的论文；专家只能看自己的评阅任务 |
| 本导师 | 导师只能看自己指导的学生 |
| 本学院 | 学院管理员只能看本学院数据 |
| 多学院 | 管理多个学院的运营人员 |
| 全校 | 研究生院或校级管理员 |
| 多学校 | 中间商平台或总部人员 |
| 平台级 | 平台配置人员，不默认查看论文正文 |

## 6.3 认证登录模块

### 6.3.1 模块定位

处理用户登录、Token、短信验证码、SSO、学校统一身份认证和外部认证适配。

### 6.3.2 功能清单

| 一级功能 | 二级功能 | 说明 |
|---|---|---|
| 普通登录 | 账号密码登录 | 支持用户名、手机号、学号登录 |
| 手机登录 | 验证码登录 | 适合专家和临时用户 |
| Token 管理 | access token | 短期访问令牌 |
| Token 管理 | refresh token | 刷新令牌 |
| 专家快捷登录 | 短信链接 | 专家通过短信进入评审页面 |
| SSO 登录 | CAS | 对接高校统一身份认证 |
| SSO 登录 | OAuth2/OIDC | 对接现代统一认证系统 |
| SSO 登录 | SAML | 对接部分高校或政企认证系统 |
| LDAP/AD | 目录服务 | 对接学校账号目录 |
| Java Adapter | 特殊适配 | 老 Java 系统、jar SDK、SOAP 接口 |
| 登录安全 | 失败锁定 | 多次失败后临时锁定 |
| 登录日志 | 登录审计 | 记录 IP、设备、时间、结果 |

### 6.3.3 学校身份获取方案

优先级建议：

1. 标准 CAS / OAuth2 / OIDC / SAML 对接。
2. 学校提供 REST API 查询学生与导师信息。
3. 学校通过 SFTP、数据库视图或 Excel 定期同步名单。
4. 遇到 Java SDK、jar 包、SOAP、特殊加密协议时使用 Java Adapter。
5. 没有接口时采用管理员导入学生、导师、专家数据作为兜底方案。

## 6.5 流程审核模块

### 6.5.1 模块定位

## 7. 关键业务流程

## 7.1 标准送审流程

```text
学生登录
→ 填写论文信息
→ 上传论文
→ 提交送审申请
→ 导师审核
→ 学院审核
→ 管理员确认送审
→ 指派专家
→ 系统通知专家
→ 专家接单
→ 专家在线评阅
→ 专家暂存/最终提交
→ 系统汇总结果
→ 判断是否需要复审
→ 管理员发布结果
→ 学生/导师查看结果
→ 生成评阅书
→ 归档
```

## 7.2 专家接审与评阅流程

```text
专家收到短信/邮件通知
→ 登录平台
→ 完善个人信息
→ 查看待评阅论文
→ 接受或拒绝任务
→ 在线查看论文 PDF
→ 填写评阅书
→ 暂存草稿
→ 最终提交
→ 系统锁定结果
→ 生成评审费记录
```

## 7.3 批量送审流程

```text
管理员创建批次
→ 批量导入学生和论文信息
→ 批量上传论文 PDF
→ 系统校验文件和信息
→ 批量审核通过
→ 批量导入专家指派表
→ 系统生成送审任务
→ 批量发送短信/邮件
→ 系统跟踪专家接单和评审进度
```

## 7.4 复审流程

```text
专家评审结果回收
→ 系统检测结果冲突
→ 标记需要复审
→ 管理员确认复审
→ 指派第三专家或重新送审
→ 专家完成复审
→ 系统重新汇总结果
→ 管理员发布最终结果
```

## 7.5 催审流程

```text
定时任务扫描评审任务
→ 判断是否临期或超期
→ 生成催审事件
→ 通知模块发送短信/邮件/站内信
→ 记录发送结果
→ 多次超期可提醒管理员重派
```

## 10. 系统性能设计

### 10.1 性能特征

平台属于典型的管理系统，具有以下特征：

```text
日常请求频率中等
毕业季集中高峰
文件上传下载压力较大
批量导入导出任务较重
通知和催审适合异步处理
统计报表适合缓存或预聚合
```

### 10.2 性能目标

| 指标 | 目标 |
|---|---|
| 普通接口响应 | 300ms - 800ms |
| 列表查询 | 1s 内，复杂统计 3s 内 |
| 文件上传 | 支持 100MB 内单文件，后期可配置 |
| 批量导入 | 1000 条以内异步处理 |
| 批量导出 | 异步生成，完成后下载 |
| 单校在线用户 | 100 - 300 |
| 专家端分散访问 | 500 - 1000 专家规模可支撑 |
| 文件存储 | 独立对象存储，不占用应用服务磁盘 |

### 10.3 性能策略

| 场景 | 策略 |
|---|---|
| 大文件上传 | 第一版普通上传，后期支持分片上传或直传 MinIO |
| PDF 预览 | 前端 PDF.js，后端提供受控文件流 |
| 批量导入 | Celery 异步任务 |
| 批量导出 | 后台生成 ZIP，完成后通知下载 |
| 短信邮件发送 | 队列异步发送，失败重试 |
| 催审扫描 | 定时任务异步执行 |
| 统计看板 | Redis 缓存或定时预聚合 |
| 专家搜索 | 初期数据库索引，后期 OpenSearch |

## 17. 风险与应对

| 风险 | 说明 | 应对策略 |
|---|---|---|
| 学校流程差异大 | 不同学校审核节点和规则不同 | 流程、规则、模板配置化 |
| 专家资源不足 | 专家接单不及时 | 专家状态管理、超时回收、重派机制 |
| 专家评审超时 | 影响整体送审周期 | 定时催审、超期提醒、管理员预警 |
| 论文泄露 | 文件属于敏感材料 | 权限控制、临时链接、访问日志、水印 |
| SSO 对接复杂 | 学校系统老旧或接口不统一 | 标准协议优先，特殊情况 Java Adapter |
| 模板差异大 | 每个学校评阅书不同 | 模板配置和版本管理 |
| 批量任务卡顿 | 大量导入导出耗时 | Celery 异步任务 |
| 权限混乱 | 多角色多数据范围 | RBAC + 数据权限统一设计 |
| 项目过度膨胀 | 功能不断增加 | P0/P1/P2 分期管理 |
| 支付合规风险 | 在线提现涉及金融合规 | 第一版线下结算，后期再接支付 |
| 数据质量问题 | Excel 导入数据不规范 | 导入校验、错误报告、预览确认 |

## 20. 最终技术结论

百杰校审平台第一阶段推荐采用：

```text
Vue 3 + TypeScript + Element Plus
FastAPI + SQLAlchemy + Alembic
PostgreSQL/MySQL + Redis + MinIO
Celery + Redis/RabbitMQ
Docker Compose + Nginx
自研状态机，后期可接 SpiffWorkflow
可选 Java Adapter 对接老旧高校系统
```

系统建设策略为：

```text
不提前微服务化
但按未来服务边界进行模块化设计
先跑通论文送审商业闭环
再逐步增强规则配置、专家匹配、AI 检测、SSO 对接和费用结算
```

最终目标是形成一套可交付、可复用、可扩展、可持续商业化的教育类论文送审平台。
