## 3. 详细问题

### Q-001 首期产品定位与运营模式

**问题描述：** 目标系统首期究竟是单校自建/私有化平台，还是由第三方服务商运营的多校送审平台，或同时支持两者。

**来源文件：**

- `docs/99_原始材料/百杰校审平台_企业级总体设计与开发文档.md`
- `docs/99_原始材料/init-resource/论文送审网站设计大纲.doc`
- `docs/99_原始材料/init-resource/1.png`
- `docs/99_原始材料/init-resource/2.png`
- `docs/99_原始材料/init-resource/3.png`

**涉及模块：** 租户组织、用户权限、论文、送审、费用、集成、部署、安全。

**当前冲突或缺失：** 材料同时描述学校内部管理、多校商业运营、委托送审和自助送审，未确定首期客户与交付模式。

**对项目的影响：** 决定租户层级、平台管理员权限、学校数据隔离、费用模型、专家库归属、合同与合规边界。

**方案 A：单校私有化优先。**

- 优点：边界最清晰；组织和权限较简单；数据合规与部署责任明确。
- 缺点：后续多校 SaaS/运营可能需要扩展租户和运营能力。

**方案 B：第三方多校运营优先。**

- 优点：符合原始材料中的商业化、多校专家资源复用方向。
- 缺点：权限、隔离、结算、合规和运营复杂度显著提高。

**方案 C：同一产品同时覆盖两种模式。**

- 优点：产品适用面最大。
- 缺点：首期范围最大，容易在需求未稳时过度设计。

**推荐方案：** 方案 A；在领域模型中保留明确的学校/租户边界，但首期不实现跨校运营功能。

**推荐理由：** 最利于先形成可验收的盲审闭环；若已有明确的第三方运营首单，应改选方案 B。

**风险等级：** P0  
**是否阻塞：** 是  
**当前状态：** DECIDED  
**最终决定：** 2026-08-03 用户确认采用方案 B：第三方多校运营优先。百杰校审平台首期按统一服务多所学校的运营平台定位设计；学校作为相互隔离的客户边界。跨校专家资源如何复用、平台运营人员能否查看学校论文正文及身份信息、各学校采用共享部署还是独立部署，继续由后续权限、安全与部署决策确定，本决定不预先授权这些能力。

### Q-002 首期论文入口与主数据来源

**问题描述：** 首期论文由学生直接填报、学校系统推送，还是管理员 Excel/批量上传。

**来源文件：**

- `docs/99_原始材料/流程图.md`
- `docs/99_原始材料/init-resource/论文送审网站设计大纲.doc`
- `docs/99_原始材料/init-resource/附件3：凡科学位论文送审平台校内送审操作指南.pdf`
- `docs/99_原始材料/init-resource/1.png`

**涉及模块：** 认证、用户、组织、论文、流程、集成、批量导入。

**当前冲突或缺失：** 主流程以学生直接提交开头，旧平台以管理员批量上传和研究生系统推送为主。

**对项目的影响：** 决定账号体系、数据主责、重复论文判定、字段可编辑性、审核起点和 SSO 优先级。

**方案 A：学生直接提交为主，管理员导入为辅。**

- 优点：端到端体验完整；符合学生在线办理目标。
- 缺点：需要学生账户、导师关系和身份数据基础。

**方案 B：研究生系统推送为主。**

- 优点：减少重复录入；学校主数据一致。
- 缺点：首期强依赖外部接口和学校配合。

**方案 C：管理员 Excel/批量上传为主。**

- 优点：最容易试点，外部依赖少。
- 缺点：学生端价值降低；人工数据质量风险高。

**方案 D：学校系统提供权威主数据，学生在百杰平台完成论文提交。**

- 优点：兼顾学校主数据一致性和学生在线提交体验；数据职责清晰。
- 缺点：首期需要学校系统对接和学生端，必须设计同步失败、迟到更新与字段冲突规则。

**推荐方案：** 方案 D。学校系统负责学号、姓名、学校、学院、专业、学位类型、导师、送审批次和提交资格；学生负责论文题目、关键词、研究方向、论文文件和相关附件。学校权威字段在百杰平台默认只读。

**推荐理由：** 既保持学校身份和资格数据的权威性，也保留学生在线提交的完整业务价值，并避免两个入口分别创建重复论文记录。

**风险等级：** P0  
**是否阻塞：** 是  
**当前状态：** DECIDED  
**最终决定：** 2026-08-03 用户确认采用方案 D。学校研究生系统向百杰平台同步学生身份、培养关系、送审批次和提交资格等权威主数据；学生登录百杰平台后补充论文内容、上传论文及附件并提交。学校权威字段默认只读，错误信息应在学校系统修正后重新同步；具体同步时机、冲突检测和异常补偿在集成设计中继续明确。

**增量决定（2026-08-10）：** 在方案 D 的权威主数据边界不变的前提下，论文进入渠道扩展为学生自提、学校单篇代传和学校批量导入。三种渠道创建统一论文记录，通过 `submission_source` 区分来源，不建立彼此独立的状态机。学校只能为已同步且具备有效批次资格的学生提交；学校提交后直接进入 `SUBMITTED`，不强制学生二次确认，学生可在本人论文列表查看该记录。送审专业必须保存受控目录中的“专业代码 + 名称”，关键词保存为去空白、去重后的字符串数组。代传操作必须记录操作者、时间和文件来源。当前前端批量导入仅实现演示预检，不代表真实 Excel 解析或批量写入 API 已完成。

**增量决定（2026-08-10）：** 学校单篇代传或批量导入后，允许同一名学校管理员继续完成材料审核和确认送审，不强制“代传人与审核人分离”；代传、审核和确认送审仍需分别记录审计日志。学生自主提交的论文被学校退回后，只能由学生本人修改论文信息和文件并重新提交，学校管理员可查看和填写退回原因，不得直接代改学生自主提交的内容。

### Q-003 核心角色与管理员模型

**问题描述：** 如何在不擅自增加角色的前提下，统一系统管理员、学生/作者、导师、专家、审核人员，并承载学校/学院/研究生院职责。

**来源文件：**

- `docs/99_原始材料/百杰校审平台_企业级总体设计与开发文档.md`
- `docs/99_原始材料/init-resource/盲审平台.docx`
- `docs/99_原始材料/init-resource/论文送审网站设计大纲.doc`

**涉及模块：** 用户、角色、权限、组织、流程、结果、审计。

**当前冲突或缺失：** 材料混用平台管理员、超级管理员、业务管理员、学院管理员、研究生院管理员等；导师又被标为可能省略。

**对项目的影响：** 直接决定页面、API 权限、数据范围、职责分离和盲审身份可见性。

**方案 A：固定五类核心角色，审核人员通过组织范围区分。**

- 优点：符合当前指定角色；角色数量可控。
- 缺点：需要细粒度权限和数据范围，配置设计要求较高。

**方案 B：按学校现实岗位拆多个角色。**

- 优点：职责直观，容易映射组织。
- 缺点：角色膨胀；不同学校难统一；违反本轮“不擅自增加角色”的边界。

**方案 C：完全基于权限包，不定义稳定角色。**

- 优点：灵活。
- 缺点：审计、测试、用户理解和默认配置困难。

**推荐方案：** 方案 A；先明确五类核心角色，学院/全校等差异作为审核人员的数据范围，不新增财务/审计等角色，除非后续被明确批准。

**推荐理由：** 最符合当前约束，同时支持组织差异。

**风险等级：** P0  
**是否阻塞：** 是  
**当前状态：** DECIDED  
**最终决定：** 2026-08-03 用户确认采用方案 A，核心角色固定为系统管理员、审核人员、学生/作者、导师、专家五类。学院秘书、研究生院人员等学校岗位不新增为核心角色，而由“审核人员 + 权限点 + 组织数据范围”表达。导师不参与送审前审批，只在结果获准发布后查看相关分数作为参考。审核人员按业务范围区分学校侧与百杰平台侧：学校侧审核人员知道学生身份、确认论文送出并查看进度和结果，但不得查看专家身份；百杰侧审核人员维护、选择和改派平台专家，只能接触匿名版论文和必要学科信息，不得查看学生与导师身份。系统管理员默认不接触论文正文、评阅内容或盲审双方身份映射。一人兼任多个角色及其他细节在角色权限矩阵中进一步约束。百杰运营侧身份可见范围已于 2026-08-04 由 Q-014 增量调整，后续设计以 Q-014 为准；本段保留原决定用于变更追溯。

### Q-004 盲审口径与匿名化门禁

**问题描述：** 首期是单盲还是双盲，哪些身份和元数据必须隐藏，匿名化失败是否阻断送审。

**来源文件：**

- `docs/99_原始材料/百杰校审平台_企业级总体设计与开发文档.md`
- `docs/99_原始材料/init-resource/盲审平台.docx`
- `docs/99_原始材料/init-resource/大纲.doc`

**涉及模块：** 论文、文件、送审、评阅、结果、权限、审计、安全。

**当前冲突或缺失：** 匿名化是核心价值，但在优先级中被列为 P2；没有匿名字段清单、处理主体和破盲流程。

**对项目的影响：** 关系到产品是否可称为盲审平台，以及论文泄露和评审公正风险。

**方案 A：首期双盲，系统自动处理并阻断失败文件。**

- 优点：保障最强。
- 缺点：自动识别、文档处理和误判处理复杂。

**方案 B：首期双盲，管理员上传/确认匿名版，系统做清单校验与隔离。**

- 优点：能形成安全闭环；实现复杂度可控。
- 缺点：依赖人工质量；仍需复核和审计。

**方案 C：首期仅做权限隔离，不做匿名化门禁。**

- 优点：实现最快。
- 缺点：正文和文件元数据可能暴露身份，不足以支撑“盲审”核心承诺。

**推荐方案：** 方案 B；把匿名版文件、人工复核、原件隔离和访问审计列为 P0，自动匿名化作为后续增强。

**推荐理由：** 在不承诺不成熟自动化的前提下满足盲审最低安全闭环。

**风险等级：** P0  
**是否阻塞：** 是  
**当前状态：** DECIDED  
**最终决定：** 2026-08-03 用户确认采用双向身份隔离和方案 A。学生提交原始版与匿名版，两个版本隔离保存；系统检测姓名、学号、导师、致谢、文件名、文档元数据等身份线索，审核人员对匿名版进行最终确认。检测或审核未通过时禁止送审，专家只能访问确认后的匿名版。专家不得看到学生、导师及可识别其身份的信息；学生和导师不得看到专家身份；专家不得看到其他专家身份和评语。审核人员仅因业务职责访问必要信息，系统管理员默认不因技术管理职责获得论文正文、评语或双方身份映射访问权；特殊访问与破盲必须授权并审计。

### Q-005 论文生命周期

**问题描述：** 需要形成唯一的论文状态集合和转换规则。

**来源文件：**

- `docs/99_原始材料/百杰校审平台_企业级总体设计与开发文档.md`
- `docs/99_原始材料/流程图.md`

**涉及模块：** 论文、流程、送审、结果、API、数据库、测试。

**当前冲突或缺失：** 两套状态数量和命名不同；缺匿名化、部分完成、撤回、终止、异议等状态。

**对项目的影响：** 状态直接进入数据库枚举、API、按钮权限、通知、统计和测试。

**方案 A：论文表承载所有细粒度业务状态。**

- 优点：查询直观。
- 缺点：状态爆炸，论文与送审任务耦合。

**方案 B：论文仅保留阶段状态，细节由审核、送审轮次、专家任务和结果聚合状态表达。**

- 优点：边界清晰，支持多轮送审和部分完成。
- 缺点：查询需聚合，设计要求更高。

**方案 C：只记录事件，状态动态计算。**

- 优点：历史完整。
- 缺点：实现和查询复杂，不适合首期。

**推荐方案：** 方案 B；在正式流程文档中建立“阶段状态 + 子实体状态 + 允许动作”矩阵。

**推荐理由：** 能避免把专家接单、结果发布和答辩资格全部挤入论文单一枚举。

**风险等级：** P0  
**是否阻塞：** 是  
**当前状态：** DECIDED  
**最终决定：** 2026-08-03 用户确认采用方案 B。论文仅表达宏观业务阶段；每轮送审由送审轮次表达，每位专家的接单与评阅由专家任务表达，“部分完成”等进度由子任务汇总得出。导师不参与送审前审批，只在结果发布后查看分数作为参考。宏观主链路为“草稿 → 已提交 → 送审准备中 → 待送审 → 送审中 → 结果处理中 → 已完成 → 已归档”；“送审准备中”只处理文件与必需材料完整性、匿名版自动检测和审核人员确认，不评价论文学术质量。正式派发专家前，学生可撤回至草稿并重新提交；派发后，学生只能提交撤回申请，由审核人员决定，批准后终止当前送审轮次、取消未完成专家任务，已提交评阅结果保留为历史但不参与最终汇总，论文返回草稿并可提交新版本。永久终止仅由审核人员执行，必须填写原因，适用于学校撤销送审资格、严重材料问题或学校正式停止本次送审；系统管理员不得作出业务终止决定。永久终止后的原流程不可恢复，重新取得资格时由学校系统同步新的提交资格并建立新的提交过程。

**当前冲突或缺失：** 专家任务与送审任务状态机重叠；改派、补审、撤回后历史关系未定义。

**对项目的影响：** 决定表结构、幂等、并发、统计、催审、结果汇总和审计证据。

## 5. 第二轮补充问题（Q-013—Q-016）

### Q-013 学校同步字段映射与批次规则配置

**问题描述：** 每个学校的同步字段、批次规则（专家人数、模板、期限、费用等）不同，是否需要在首期就统一字段字典和规则实例。

**最终决定：** 2026-08-04 用户确认：不预先冻结全校统一的字段字典。每个学校通过租户级 JSON 配置同步字段映射（映射可版本化调整）；批次规则（专家人数、评阅模板、期限、费用等）当前不设置默认值，等各学校提供后再配置。正式文档已把”字段映射配置”写入同步需求与架构，批次规则保持版本化可配置。

### Q-014 百杰运营侧数据可见性

**问题描述：** 平台运营方（百杰）侧人员能否查看学生与专家身份信息。

**最终决定：** 2026-08-04 用户确认：百杰运营侧（百杰侧审核人员及必要的平台管理职能）可以查看学生与专家身份信息，以支撑派单、进度、结果和费用结算管理；该可见性必须受审计与数据范围约束，不构成跨校数据共享，也不改变专家与作者/导师之间的双向盲审隔离。系统管理员默认仍不接触论文正文、评阅内容或盲审映射；学校侧审核人员始终不得识别专家。正式文档已按此更新信息分区、权限矩阵、数据投影与测试验收。

### Q-015 送审专业方向与评分模式

**问题描述：** 学生是否按专业选择送审范围，评阅与汇总采用什么评分方式。

**最终决定：** 2026-08-04 用户确认：学生提交时按平台专业/学科目录选择本篇论文的送审专业方向；专家维护个人资料时填写擅长评审领域，派单按专业方向与擅长领域匹配候选并执行回避。评阅支持分项打分（系统计算平均分）或直接总分加评语两种模式，由学校/批次规则版本化配置；返还结果时展示分数与获准评语。学生按专业方向选择不等于指定具体专家。

### Q-016 导师与专家账号来源

**问题描述：** 导师账号与平台专家账号分别来自哪里。

**最终决定：** 2026-08-04 用户确认：学生与导师共用学校身份渠道（SSO）登录；平台专家使用平台自建账号登录并维护个人资料。正式文档已按此更新认证设计。

### Q-017 第二批甲方演示范围与主线规则

**问题描述：** 甲方演示是只完成单篇论文黄金流程，还是同时补齐四端管理列表；演示批次使用多少名专家。

**最终决定：** 2026-08-10 用户确认采用方案 C：用一篇主线论文连续演示学生提交、学校审核、百杰派单、专家评阅、学校发布和学生查看，同时为每个角色补齐多状态管理表格。演示批次配置 1 名专家、300 元任务费用和六项 100 分动态评阅模板。单专家和具体金额仅是演示批次规则快照，通用平台仍支持学校/批次配置多专家、费用和评阅模板。原 PAGE-007 扩展为送审运营台，并新增 PAGE-024 学校账户与账单。

### Q-018 演示实现改为按角色交互闭环验收

**问题描述：** 第二批页面虽然补齐了视觉内容和路由，但多数页面仍是静态演示数据，缺少可点击的允许动作、状态变化、详情和异常反馈；学生端专业选择器的呈现也与既定页面规格不一致。

**涉及文档：** PAGE-002、PAGE-003、PAGE-012 页面原型，第二批演示规格、实施计划、编码准入检查表与需求追踪矩阵。

**对系统的影响：** 不能再以“页面存在”作为功能完成标准。角色页面必须按真实权限提供可执行动作，并由共享状态模型反映操作结果；当前没有实现的后端能力必须明确标注演示边界。

**最终决定：** 2026-08-11 用户确认停止同时扩展所有角色，改为按角色逐个设计、评审、编码和验收。每个角色完成后再进入下一个角色。角色验收至少包括：页面入口真实可达、允许动作可以点击、动作反馈明确、状态和可用操作随动作变化、详情和异常状态可查看、刷新后的演示状态策略明确、移动端关键流程可用。第一轮从学生端开始；学生端详细交互范围需经用户评审后写入独立规格和实施计划。
