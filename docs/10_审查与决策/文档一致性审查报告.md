## 3. 项目总体理解

本项目是百杰运营、面向多所学校的论文双向盲审平台。学校系统提供身份、组织、批次和资格等权威主数据；学生在平台补充论文并上传原件和匿名件；学校审核人员识别学生但不识别专家，负责材料确认、进度、发布和异议；百杰审核人员识别专家，且为支撑派单、进度、结果和费用管理可查看学生/导师身份，但不构成跨校共享也不解除双盲；专家仅处理本人接受的匿名任务，填写擅长评审领域；导师只在发布后查看本人学生的结果作为参考，与学生共用学校 SSO；专家使用平台自建账号。

P0 目标是从资格同步、提交、匿名门禁、人工指派、专家接拒/评阅、超时改派、汇总冲突、发布异议，到费用提现、通知审计、导出和基础恢复的可运营闭环。自动匹配、自动匿名生成、完整在线复核和自动代付进入 P1；AI、深度查重、小程序、高级分析和服务化进入 P2。

## 5. P0 阻塞问题

原审查中的定位、五角色、双盲、状态模型、任务边界、汇总发布、MVP 和追踪门禁等 P0 业务问题均已形成决定，并写入正式草稿。第二轮用户评审（Q-013—Q-016）已确认并同步：学校同步字段映射、百杰运营可见性、送审专业方向与评分模式、导师/专家账号来源。第二轮结构性补齐（2026-08-04）已完成：02 流程结构化展开与状态退出条件、03 模块调用关系。当前未发现新的互相冲突、必须重新讨论才能继续文档评审的 P0 业务问题。

仍存在三项不可绕过的流程性编码阻塞：

1. 尚未编制并确认按可独立验收增量拆分的实施计划；
2. 首个学校的认证/同步协议与字段映射、批次规则实例尚未提供；
3. 用户尚未明确回复”批准进入编码阶段”。

这些阻塞不能通过”资料已经较完整”推定解除。

## 6. P1 重要问题

1. 学校认证/同步协议、各校字段映射的具体 JSON 结构和测试端点尚未提供，对第一实施增量构成输入阻塞；映射机制已按租户配置设计，字段字典待各校提供。
2. 数据库目前是 40 张逻辑表的聚合级设计，核心字段、约束 DDL、索引容量和迁移顺序需按实施增量细化。
3. API 已有 34 组资源/动作，但请求响应 Schema 和真实 OpenAPI 尚未冻结。
4. 各学校的专家人数、评阅模板（含评分模式）、汇总/冲突、异议期限、费用和通知规则需以版本化批次配置落地，不能设置未经确认的默认业务值。
5. 负载规模、目标部署环境、正式 RPO/RTO 和浏览器矩阵尚需真实输入。
6. 自动支付供应商、合同、实名、税务和对账规则尚未确定，因此严格保留在 P1。

## 8. 文档之间的矛盾

原始材料的以下矛盾已经通过用户决定消解：高校自建与多校平台、学生提交与学校推送、导师审批、单盲/双盲、单状态/多层状态、自动/人工匹配、线上/线下支付、技术栈分叉。

首轮草稿自查发现并修正了两项内部问题：

- 论文撤回申请与专家提现申请曾拟用同名表，已改为 `thesis_withdrawal_requests` 与 `withdrawal_requests`；
- 论文 `COMPLETED` 曾隐含”异议已办结或无异议”的未确认期限，已改为结果发布即完成，异议作为独立流程；未配置期限时系统不得猜测。

第二轮调整（Q-013—Q-016）修改了此前文档间的两处不一致：

- 百杰侧”不得识别学生/导师”的旧表述已全面更新为”运营侧可见学生与专家身份、受审计约束”，涉及架构信息分区、权限矩阵、API 投影和测试验收；
- 专家任务 `OVERDUE` 独立状态已移除，改为逾期标记；论文 `ARCHIVED` 状态已移除，改为归档标记。状态枚举已在 02 产品设计形成唯一表，并与数据库状态字段映射一致。

第三轮结构性补齐未引入新的业务矛盾，仅新增流程结构化、模块调用关系与状态退出条件。

## 9. 未被任何文档充分覆盖的功能

以下不是遗漏的 P0 闭环，而是实施级或后续范围尚未充分设计：

- 学校 SSO/同步的具体协议和字段字典（含各校 JSON 映射结构）；
- 特殊解盲的组织审批人和操作手册；
- 完整在线复核的页面、状态、API 和测试；
- 自动支付、对账、税务和失败补偿；
- 正式数据保留/销毁期限和离校离职处置；
- 高级统计、AI、查重、小程序、多地域和服务化。

对应 P1/P2 功能在进入自身实施前必须补齐追踪链，当前不得创建空实现。

## 10. 重复或过度设计的内容

原始材料和代码骨架预设了大量模块、空文件、多种 SSO、存储、数据库、队列和 Java Adapter。正式设计已收敛为模块化单体、单一主技术栈和按真实需要引入适配器。`java-adapter/` 目录按用户决定保留，仅在真实学校 Java 对接需求出现后启用，不作为 P0 实现承诺。通知、文件、审计和工作流分别明确所有权，避免每个业务模块重复建设基础能力。

未来仍需警惕把 40 张逻辑表一次性全部实现；实施计划应按最小闭环增量，只创建当前增量需要且已确认的结构。

## 11. 可能超出 MVP 的内容

已明确不进入 P0：自动专家推荐、自动匿名生成、完整在线复核、自动代付、多渠道增强、AI、深度查重、小程序、高级分析、微服务、Kubernetes、多地域和空业务占位。P0 保留的费用、异议、备份等能力均是最小可运营版本，不等同于其完整长期形态。

## 12. 安全和隐私风险

最高风险仍是跨租户访问和盲审身份泄露。当前设计采取应用过滤 + PostgreSQL RLS、原件/匿名件分域、短时下载授权、分端数据投影、服务端对象权限、关键下载审计和特殊解盲控制。第二轮明确了百杰运营侧身份可见性边界：可见性用于派单、进度和费用管理并受审计约束，不等于学校间数据共享；实现与测试必须证明该边界有效。

次要高风险包括后台任务跨租户上下文丢失、导出混入身份、日志/通知泄露正文、管理员绕过、匿名件元数据残留和备份访问过宽。上述均已进入开发、测试或运维规范。

## 13. 数据库和 API 风险

- 共享数据库要求每个租户业务表、查询、唯一约束、索引和后台任务正确带租户上下文；
- 平台共享专家表和租户专家任务之间的边界必须通过仓储与 API 投影保持；
- 三层状态不允许由控制器或 SQL 直接修改；
- 指派、提交、发布、计费和提现需要幂等与并发约束；
- 字段级 Schema 尚未冻结，在冻结前不得生成迁移或业务接口；
- 错误响应、日志和 `404/403` 策略必须避免资源枚举和身份泄露。

## 14. 测试验收风险

设计层已有 P0 追踪，但测试尚未实现。必须重点覆盖两个租户的真实 RLS、五角色允许/拒绝、文件用途越权、匿名命中、上传失败、重复提交、并发派单、接受/评阅超时、改派、最终锁定、补审重算、发布前后投影、账务幂等、学校字段映射配置和数据库/对象联合恢复。缺少任何跨租户、双盲或恢复证据均不得上线。

## 15. 推荐处理顺序

1. 用户评审本轮 00—09、ADR 和追踪矩阵，集中提出需要修改的业务内容（第二轮已完成）；
2. 根据评审修改，并完成第三轮跨文档一致性检查（流程结构化、模块调用关系已完成）；
3. 获取首个学校的认证/同步、批次规则和目标环境输入；
4. 对首个实施增量细化字段级数据库、API、页面和可执行测试；
5. 执行编码准入审查；
6. 编制并由用户确认实施计划；
7. 仅在用户明确回复”批准进入编码阶段”后开始首个增量。

## 16. 是否具备进入下一阶段的条件

项目已完成第二轮用户评审、第二轮与第三轮一致性检查以及流程/模块关系结构性补齐，仍不具备编码准入或代码开发条件。下一阶段应获取学校接口与批次规则输入、执行编码准入审查、编制实施计划，不应开始补脚手架、数据库迁移、接口或页面。
