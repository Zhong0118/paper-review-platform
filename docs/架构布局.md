下面给你一版适合 **百杰校审 / 论文送审平台** 的整体项目文件夹布局。这个布局按你之前确定的方向设计：

> **前后端分离 + FastAPI 模块化单体 + 轻量 DDD + MVP 分阶段交付 + 后期可拆微服务**

建议采用 **Monorepo 单仓库结构**，也就是前端、后端、部署、文档、脚本放在一个总项目里，方便早期开发和交付。

---

# 1. 项目总目录结构

```text
baijie-review-platform/
├── README.md
├── LICENSE
├── .gitignore
├── .env.example
├── docker-compose.yml
├── docker-compose.dev.yml
├── docker-compose.prod.yml
├── Makefile
│
├── docs/                         # 项目文档
├── frontend/                     # 前端项目 Vue 3
├── backend/                      # 后端项目 FastAPI
├── java-adapter/                 # 可选 Java 对接服务
├── deploy/                       # 部署相关
├── scripts/                      # 工具脚本
├── data/                         # 本地开发数据/模板/示例数据
├── storage/                      # 本地开发文件存储挂载目录
└── tests/                        # 端到端测试/集成测试
```

说明：

```text
frontend     前端 Vue3 管理端、学生端、专家端
backend      FastAPI 主业务系统
java-adapter 学校老系统/Java SDK/SSO 特殊对接服务，前期可为空
deploy       Nginx、Docker、CI/CD、服务器部署配置
docs         产品、需求、架构、数据库、接口、流程图文档
scripts      初始化、迁移、导入、导出、备份脚本
data         Excel 模板、评阅书模板、测试数据
storage      本地开发时模拟 MinIO/文件存储
```

# 2. 后端目录结构：FastAPI 模块化单体

后端是核心，建议按**领域模块**拆，而不是按简单 controller/service 混在一起。

```text
backend/
├── README.md
├── pyproject.toml
├── requirements.txt
├── requirements-dev.txt
├── .env.example
├── alembic.ini
├── Dockerfile
│
├── app/
│   ├── main.py                    # FastAPI 入口
│   ├── api.py                     # 总路由注册
│   ├── lifespan.py                # 启动/关闭生命周期
│   │
│   ├── core/                      # 核心配置与基础能力
│   ├── db/                        # 数据库连接与基础模型
│   ├── modules/                   # 业务模块
│   ├── shared/                    # 跨模块共享能力
│   ├── workers/                   # Celery 异步任务
│   └── tests/                     # 后端单元测试
│
├── alembic/                       # 数据库迁移
├── logs/                          # 本地日志
└── tmp/                           # 临时文件
```

每个模块都建议采用统一结构：

```text
模块名/
├── router.py                      # 接口层
├── service.py                     # 应用服务层
├── domain.py                      # 领域逻辑，可选
├── repository.py                  # 数据访问层
├── model.py                       # ORM 模型
├── schema.py                      # Pydantic 请求/响应模型
├── permissions.py                 # 本模块权限
├── enums.py                       # 状态枚举
├── events.py                      # 事件定义
├── tasks.py                       # 本模块异步任务，可选
└── tests/                         # 模块测试
```

MVP 阶段可以先不写 `domain.py`，等业务复杂后再拆。

# 14. 最关键的落地建议

你的项目不要一开始只建几个简单目录：

```text
api/
models/
services/
utils/
```

这种结构前期看起来简单，后期会乱。

也不要一开始搞成真正微服务：

```text
auth-service/
user-service/
thesis-service/
expert-service/
review-service/
```

这会增加部署和联调成本。

最合适的是：

```text
单仓库 Monorepo
前后端分离
后端模块化单体
每个业务模块独立 router/service/repository/model/schema
异步任务单独 workers
外部系统对接单独 integration
特殊高校 Java 对接单独 java-adapter
```

一句话总结：

> **目录结构按照未来可拆微服务的边界设计，但当前以模块化单体实现。这样既不会过度工程化，也不会后期变成一坨代码。**
