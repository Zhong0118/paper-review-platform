# 论文盲审平台后续开发规划

> 执行方式：每次只推进一个切片，默认在当前任务 inline 执行。进入编码时使用 executing-plans；先阅读对应切片规格，再逐项完成测试、实现、验收。本文是项目级规划，近期工作包细化到验收场景；不把远期路线当成已经完成设计的代码实施方案。

**Goal:** 先交付可信的单专家真实闭环，再建设可配置、多专家、可运营的平台，最终按明确学校场景完成上线验收。

**Architecture:** 保留现有模块化单体与论文/版本/轮次/任务分层；围绕业务切片同时交付服务端规则、页面操作与验证。真实业务逐步脱离演示服务，不进行全站重写。

**Tech Stack:** Vue 3、TypeScript、FastAPI、SQLAlchemy 2、Alembic、PostgreSQL；异步任务与私有对象存储随对应需求引入。

**依据:** [现状评估](../../reviews/2026-09-21-project-assessment-and-roadmap.md)、[CURRENT](../../CURRENT.md)、现行切片规格及用户对后续规划方向的认可。

## 1. 本轮约定与成功标准

- 本文交付开发路线、优先级、工作包、职责和验收方法，不启动业务代码修改。
- 规划假设：用户主导产品与业务判断，AI 协助开发；没有已确认的交付日期、团队规模和学校接入协议。
- 第一里程碑仅用虚构身份、真实格式测试 PDF、平台账号、单专家验证闭环；不代表获准承载真实学校数据。
- 后续按里程碑排期，先完成首批小任务测得实际速度，再给日期。没有依据时不承诺“几周上线”。
- 每项功能完成必须同时具备：真实接口、服务端权限/状态约束、可操作页面、异常反馈、验收证据。无页面需求的底层能力以集成测试验收。

全局约束：租户来自 token；`theses.stage` 只由 workflow.transition 修改；学校不见专家身份；专家不见作者和原始版；冻结 scenarioService 的业务扩展；测试使用 5433/paper_review_test；原始材料目录只读；RLS 在真实数据上线前完成。

## 2. 开发路线的取舍

选择“先加固现有闭环，再逐片增加运营能力”。保留已经验证的业务模型，优先修复真实材料与权限问题，投入可直接转化成可靠功能。

暂不选择两条路线：直接补齐所有旧 P0 会让基础缺陷扩散到更多功能；整体重写会重复消耗已有成果，且无法自动解决尚未明确的业务规则。

三个产品节点：

| 节点 | 定义 | 不应误认为 |
|---|---|---|
| 开发验收版 | 虚构身份+真实 PDF，多角色闭环与异常分支通过 | 可以直接交给真实学校使用 |
| 受控试点版 | 约定学校/批次/规则下可运营；通过隔离、恢复、部署验收 | 所有学校均可直接接入 |
| 正式运营版 | 在试点基础上补齐约定合同范围、收费/接入/运维能力 | 已包含全部 P1/P2 |

| 编号 | 交付 | 工作范围 | 验收出口 | 依赖 |

| M5 | 商业运营与学校接入 | 学校额度/账单、专家费用/提现/线下付款回填；SSO、同步、代传/批量导入 | 账务可核对；同步幂等；批量有逐项结果 | 规则快照和主链稳定；按试点需求调整 |
| G | 真实数据上线门禁 | RLS、私有存储、生产认证、全链审计、备份恢复、监控、迁移与容量测试 | 两租户隔离、数据库+文件恢复、升级与故障演练有证据 | 贯穿各里程碑，真实数据上线前必须完成 |

M3 必须把多专家派单和最小汇总作为同一可验收能力交付，不能先放开多个任务、仍用“第一个分数”发布。冲突阈值尚未确认时，不开放声称支持该规则的真实批次。

G 不是最后一项排队工作：文件审计从 7A 做，CI 从 M0 做，RLS 在 M2 明确租户/平台数据边界时推进，恢复演练在部署验证时做。首个学校要求 SSO 或收费时，M5 对应工作前移到试点前。

## 6. 每个切片固定的工作方式

1. **规格**：写明问题、范围、非目标、数据/API、允许动作、权限、失败行为和验收；遇到学校制度问题由用户定，常规技术选择用最简单实现。
2. **回归测试**：缺陷先复现；使用真实 HTTP、真实 Postgres 和真实格式测试材料。前端测试不得只验证测试文件自己定义的映射函数。
3. **最小实现**：同时交付必要前后端修改；不顺手清空目录、不全站重构、不在 scenarioService 加真实业务。
4. **验证**：定向测试 → 受影响集成测试 → 类型检查/构建；涉及迁移就测迁移，涉及角色流程就验收浏览器。
5. **自查**：代码与规格核对；重点看多租户、同租户不同用户、文件/任务关系、重复请求、并发与历史记录。
6. **交付**：提交清晰变更记录；更新 CURRENT 的真实状态、测试证据、未解决项及唯一下一步。

任何测试失败先判断是实现问题、测试假设还是环境问题；不能跳过失败来标记完成。每包完成后保留可运行状态，不用“后续页面会补上”代替本包必需操作。

CI 随 M0/M1 建立：独立 Postgres 服务、后端回归、前端单测与构建、迁移验证；浏览器主链完成后加入。锁定运行依赖，避免本机通过但新环境无法复现。
