# T06：数据库行隔离设计（R09 交付）

状态：**修订稿经独立复核在设计层放行；尚未实施**。原稿日期：2026-09-23，修订日期：2026-09-24。基线为 `codex/slice-7a1-file-integrity` / `39a8962` 上未提交的 T01–T05、R01–R08；[R08 验收](../../reviews/2026-09-23-r08-validation.md)是本设计的前置证据。[原独立审查](../../reviews/2026-09-24-t06-rls-design-review.md)的五项发现已纳入下文，[修订稿复核](../../reviews/2026-09-24-t06-rls-design-rereview.md)允许单独启动 T06-1；真实非 owner 策略测试属于后续实施验收。

## 目的与边界

首批仍是单校、20 篇以内、单专家和平台账密，但数据库必须按多校隔离设计。成功标准是：使用**真正的普通运行数据库账号**，即使 ORM 查询漏了 `tenant_id` 条件，也读不到或改不了其他学校的数据；学生、导师、专家、学校、平台审核和系统管理员仅获得下表列出的行。学校不能通过 API 获得专家身份，专家不能获得原文或作者；原有服务层授权、投影和 404 契约继续生效。RLS 是第二道行级防线，不替代文件对象存储权限、列级保密、JWT 验证或审计。

本规格只设计 T06。R09 不运行 `CREATE ROLE`、迁移、RLS SQL 或生产配置。部署主机、账号名称和密钥由后续环境决定；试点真实数据、Hosted CI、备份恢复和放行仍未获证实。

## 现状与表清单

现有 `backend/app/db/session.py` 用一个 `DATABASE_URL` 建立 `AsyncSession`；`get_current_user` 在同一 session 内先读 `users`、`roles`、`user_role_assignments`、`tenants` 和 `tenant_user_memberships`。`/auth/login` 与 `/auth/refresh` 没有已认证 actor；`file_reader` 的专用 token 会再次调用 `load_active_identity`。`alembic/env.py`、`seed.py`、`tests/conftest.py` 和隔离验收入口目前也共用或派生同一连接配置。因此不能只在 `theses` 加策略后宣称全链路受保护。

按当前 ORM `__tablename__` 核对为 **28 张表**。带 `tenant_id` 的 16 张：`organizations`、`review_batches`、`discipline_catalog`（可为空，表示全局目录）、`tenant_user_memberships`、`user_role_assignments`（平台角色可为空）、`student_eligibilities`、`theses`、`thesis_versions`、`file_objects`、`review_rounds`、`expert_tasks`、`result_summaries`、`objections`、`workflow_events`、`termination_records`、`audit_events`（系统/未认证事件可为空）。不带 `tenant_id` 的 12 张：`tenants`、`users`、`roles`、`auth_sessions`、`experts`、`expert_conflicts`、`thesis_version_files`、`anonymization_checks`、`review_drafts`、`review_result_versions`、`result_publications`、`idempotency_keys`。后一组必须按 actor、父表或全局目录规则处理，不能默认放行。

**T06-6 实施校正（2026-09-28）：** 原矩阵遗漏了现行调用链：学生 `submit()/withdraw()` 在同一事务插入 `workflow_events`；专家 `submit_final()` 在同一事务写 `result_summaries` 并插入 `results_ready` 事件。`INSERT ... RETURNING` 还要求新事件对专家本人满足 SELECT 策略。实施仅给学生本人论文的提交/撤回动作、专家本人已提交任务对应轮次的封轮次汇总及 `results_ready` 事件开口；专家在封轮次后不能 UPDATE 汇总，学校发布后任何业务角色不能 UPDATE 汇总。此为维持已存在主链所需的最小权限修正，详细验证见 [T06-6 记录](../../reviews/2026-09-28-t06-6-validation.md)。

`expert_tasks` 对学生/导师改为无直接数据库读取：现有 `published_result()` 通过 `school_results()` 联查任务，是实现复用而非学生/导师的授权需求；T06-7 要改为仅从已发布 `result_summaries.result_task_ids` 读取对应正式结果。学校发布时仍校验任务归属、状态、轮次和分数；学生/导师读取时校验结果数量、当前标记和汇总分数，维持原有匿名响应。学生 `withdraw()` 会把本人 `CREATED` 轮次改为 `CANCELLED`，所以学生对 `review_rounds` 的 SELECT/UPDATE 不能遗漏；本人轮次在取消后仍须满足 SELECT 策略，因为 UPDATE 读取目标列时也会检查 SELECT 策略，写权限只服务于这条已存在的撤回路径。[PostgreSQL 16 CREATE POLICY](https://www.postgresql.org/docs/16/sql-createpolicy.html)。API 可见结果和角色权限不变。

**T06-7 实施校正（2026-09-28）：** 仅靠 `result_summaries.result_task_ids` 放行 `review_result_versions` 会让一个被污染的已发布汇总引用外校任务 ID，而学生没有 `expert_tasks` 行权限可供策略校验。正式结果因此新增非空 `round_id`、`tenant_id`，从任务回填，并以 `(task_id,round_id,tenant_id)` 复合外键固定任务归属。学生/导师的结果 SELECT 同时要求任务 ID 在本人可见汇总中、结果轮次和租户与汇总一致、结果为当前版本；发布 API 的学校集合校验保持原样。专家最终提交在已锁任务仍为 `IN_REVIEW` 时先 flush 结果，随后在同事务标记 `SUBMITTED`，使结果写策略在提交后立即关闭；不改变任务/论文锁获取顺序。[T06-7 验收记录](../../reviews/2026-09-28-t06-7-validation.md)包含外校任务 ID 注入负向测试。

## 信任边界与会话

1. **三种数据库身份**：迁移/种子 owner、普通业务运行账号、受限认证账号。业务账号必须 `NOSUPERUSER NOBYPASSRLS` 且不是任一受保护表 owner，也不能通过角色成员关系继承/切换到 owner 或认证账号；认证账号只获身份表、`auth_sessions` 与匿名拒绝审计所需权限，不能访问论文、文件或结果表。`DATABASE_URL` 留作业务连接；后续新增认证与迁移 URL，不能让 Alembic 静默使用业务账号。测试账号可按随机名临时创建，结束精确删除；R09 不创建。
2. **认证前入口**：`/auth/login`、`/auth/refresh`、`/auth/logout` 使用受限认证 session；它可读取账号、角色分配、学校及 membership 状态，锁 `users` 和 `auth_sessions`，只更新登录时间、会话行等所需字段。`tenants` 在 T06-4 启用 RLS 时必须给认证数据库账号单独的 SELECT 策略，允许读取包括 `SUSPENDED` 在内的租户行，列权限只含 `id`、`code`、`status`；`load_active_identity()` 仍负责拒绝非 ACTIVE 租户，认证账号不得获得 `organizations`、论文、文件或结果权限。认证查询须只加载被授予的列。系统/学校撤销仍由已认证业务 session 执行，锁顺序保持 R02 的 User→AuthSession；不得通过宽泛业务 RLS 放开“用户名查询所有账号”。
3. **已签名 token 到业务上下文**：`get_current_user` 先校验 token 签名、类型、有效期与声明格式，再在**第一条身份查询前**，在当前事务用 `set_config('app.user_id', ... , true)`、`app.role`、`app.tenant_id` 设置候选上下文。RLS 只让该 actor 读本人身份行和必要的角色/学校行。`load_active_identity` 再检查数据库中的 `auth_version`、角色、学校、membership；不匹配立即回滚并拒绝，绝不进入业务 service。文件专用 token 走同一流程。客户端传来的 `tenant_id`、未验签 token 或请求头不可作为上下文来源。
4. **事务生命周期**：`SET LOCAL`/`set_config(..., true)` 只在当前事务有效；`get_session` 退出时回滚未完成事务。成功 `commit` 后若同一请求再查数据库，必须开启新事务并显式重绑已验证身份，否则按无上下文拒绝。禁止 session 级 `SET`，禁止把带上下文的 session 跨请求复用。`begin_nested` 前完成绑定，测试覆盖 savepoint 回滚、普通回滚、异常和连接池复用。当前路由多在返回前 commit，实施时仍需逐一检查。
5. **上下文不是数据库内的防伪凭据**：普通 PostgreSQL 自定义 GUC 可由持有该数据库连接并能运行任意 SQL 的代码改写。该方案针对应用漏写过滤条件提供防线，**不能单独抵御取得业务 DB 凭据或任意 SQL 执行能力的攻击者**。生产账号权限、参数化查询、密钥保护及更强连接隔离属于 T09 放行条件；不得在报告中把 RLS 说成这类攻击的完整防护。
6. **后台/维护路径**：目前没有可据此放行的生产后台作业。未来定时任务和消息消费者必须使用普通业务账号，并在每个事务显式绑定已验证的业务 actor 或独立审查过的任务身份；无身份即拒绝，不能借用迁移 owner。当前 `seed.py` 和验收场景属于虚构数据准备，须在隔离 schema 中于 RLS 启用前准备，或经真实业务 API 准备；生产不运行默认 seed。

## 策略形状与关系约束

每张业务表在 `0011–0015` 迁移集合中建立对应策略；最终 head 对 28 表全部 `ENABLE ROW LEVEL SECURITY` + `FORCE ROW LEVEL SECURITY`，中间 revision 不作为可部署版本。未列出的命令默认拒绝。先以 `GRANT` 缩小表/列权限，再用 `FOR SELECT/INSERT/UPDATE/DELETE` 的 `USING` 与 `WITH CHECK` 分开写。PostgreSQL 对无适用策略采取默认拒绝，表 owner 通常绕过而 `FORCE` 可约束 owner；superuser/`BYPASSRLS` 始终绕过。[PostgreSQL 16 行安全说明](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)、[CREATE POLICY](https://www.postgresql.org/docs/16/sql-createpolicy.html)。

建议在迁移中定义仅读取事务 GUC 的 `app_actor_id()`、`app_tenant_id()`、`app_role()`，用 `nullif(current_setting('app.user_id', true), '')::uuid` 一类表达式使缺失/空上下文为 NULL，从而策略结果不为 TRUE；函数固定 `search_path`、不读表、不用 `SECURITY DEFINER`。角色代码只接受六个现有 `RoleCode` 值。平台审核和专家 `tenant_id=NULL` **从不**被解释成“所有学校”；跨校读取必须写出 `app_role()='platform_reviewer'` 且仅用于上述运营表。系统管理员只对元数据表有显式策略。

业务/认证账号只有受保护 schema 的 `USAGE` 和必要表/函数权限，没有 `CREATE`、`TRUNCATE`、`REFERENCES` 或改策略权限；创建策略和 helper 函数的 owner 不用于 HTTP。RLS 关系谓词不能把 `tenant.status='ACTIVE'` 或目标 `membership.is_active` 当作可见性的通用条件：暂停学校会在同一事务中撤销成员会话，停用成员也要先改状态再撤销。身份是否有效由现有 `load_active_identity` 判定；管理命令仍需看见被暂停/停用的目标行，并按现有锁顺序完成撤销。

**密码哈希列权限决定：** 普通业务账号对 `users` 仅获除 `password_hash` 外、业务查询所需列的 SELECT；学校/系统的账号创建与重置另获按现有业务角色 RLS 约束的 `password_hash` INSERT/UPDATE，绝不授予该列 SELECT。现有 `select(User)` 会加载整行，T06-3 须将 `User.password_hash` 配为默认 deferred，认证登录显式加载哈希，其余身份/管理查询不触发懒加载；密码重置只赋新值。认证账号为登录验证获得 `password_hash` SELECT，按查询实际使用的其他列单独授权。直接 SQL 要证明业务账号读哈希被拒，认证账号可验证密码而不能读论文，现有登录和重置 API 不变。[SQLAlchemy 2 列延迟加载说明](https://docs.sqlalchemy.org/en/20/orm/queryguide/columns.html)。

策略表达式的基准示例（列名以现有模型为准，实施任务要逐表展开）：

```sql
-- 论文：学生本人、学校本校、平台运营；专家另由有效任务关联的 SELECT 策略放行。
CREATE POLICY thesis_student_select ON theses FOR SELECT TO paper_app
USING (theses.tenant_id = app_tenant_id() AND app_role() = 'student'
  AND EXISTS (SELECT 1 FROM tenant_user_memberships m
              WHERE m.id = theses.student_membership_id AND m.user_id = app_actor_id()));
CREATE POLICY thesis_student_insert ON theses FOR INSERT TO paper_app
WITH CHECK (theses.tenant_id = app_tenant_id() AND app_role() = 'student'
  AND EXISTS (SELECT 1 FROM tenant_user_memberships m
              WHERE m.id = theses.student_membership_id AND m.user_id = app_actor_id()));
-- 子表：不能只检查自己的 tenant_id，必须验证父行属于同一学校。
CREATE POLICY round_school_insert ON review_rounds FOR INSERT TO paper_app
WITH CHECK (app_role() = 'school_reviewer' AND review_rounds.tenant_id = app_tenant_id()
  AND EXISTS (SELECT 1 FROM theses t
              WHERE t.id = review_rounds.thesis_id
                AND t.tenant_id = review_rounds.tenant_id)
  AND EXISTS (SELECT 1 FROM thesis_versions v
              WHERE v.id = review_rounds.thesis_version_id
                AND v.thesis_id = review_rounds.thesis_id
                AND v.tenant_id = review_rounds.tenant_id));
```

所有策略子查询都须显式限定**内层和外层**同名列；上述三处修正是示例，不是 28 表的完整 SQL。真正执行前，以 A/B 已知 UUID 测试每个 INSERT/UPDATE 的父 ID 混搭。PostgreSQL 会优先将未限定同名列绑定到内层表，原稿的 `v.thesis_id = thesis_id` 等条件实际是自比较。

**解除轮次/论文策略回环。** `review_rounds` 必须让学生看见并取消本人待送出轮次，而专家的 `theses` SELECT 不能再反查轮次，否则同一业务数据库角色上的 SELECT 策略互相展开。T06-5 为 `expert_tasks` 新增非空 `thesis_id`：从其 `round_id` 对现有行回填，先核对旧数据关系，再用复合外键保证 `(round_id, thesis_id, tenant_id)` 与 `review_rounds` 一致；新派单/改派写入已锁定论文的 ID。专家任务的本人 SELECT 只查 `experts.user_id=app_actor_id()`，不反查轮次；专家论文 SELECT 直接按任务 `thesis_id`、本人专家 ID 和允许状态授权。这样 `review_rounds` 的学生 SELECT/UPDATE 可经其 `thesis_id` 查本人论文，专家轮次 SELECT 可经本人任务查到轮次，均不形成反向引用。专家的 `thesis_versions` 行 **不授予 SELECT**：邀请列表只需要标题，而整行还含摘要/关键词。T06-5 给 `review_rounds` 增加非空 `anonymous_title` 快照，从轮次版本回填，确认送出时写当前版本标题；专家列表与邀请从本人可见轮次读取该字段。`thesis_version_files` 的专家 SELECT 分支仅经轮次、本人任务和可见论文验证当前匿名文件，不依赖专家能读版本行；其他角色仍按版本父链。匿名正文只允许 `IN_REVIEW`、轮次 `ACTIVE`、论文 `UNDER_REVIEW`。旧任务 `CANCELLED` 不得继续授权文件。

**文件、发布与列范围。** 文件 purpose 在数据库中是小写 `'anonymous'`，两处 `file_objects.purpose`、`thesis_version_files.purpose` 均使用此值；原文为 `'original'`。`thesis_version_files` 的 SELECT 只查版本、任务与轮次，不反查 `file_objects`；文件行的专家 SELECT 可以查 link，且需同时满足任务 `IN_REVIEW`、轮次 `ACTIVE`、论文 `UNDER_REVIEW`、当前版本和匿名 purpose。link 的 INSERT/UPDATE 也不能查询 `file_objects` 的 SELECT 策略，否则会经 `file_objects→thesis_version_files` 回环。T06-5 先为 `file_objects` 增加 `thesis_id`：新上传必须写入所属论文；旧行从 `upload_version_id` 或已关联 link 的版本推导，若两条来源指向不同论文则迁移拒绝，无法唯一推导的旧孤儿行可保留 NULL 但不能被新的 link 引用。T06-7 为 link 新增非空 `tenant_id` 与 `thesis_id`，按版本回填，并以 `(thesis_version_id,thesis_id,tenant_id)` 和 `(file_id,thesis_id,tenant_id,purpose)` 两个复合外键分别约束版本与文件属于**同一篇论文**；`WITH CHECK` 仅检查 actor、link 本行及可见版本，不能反查文件。原有草稿复制 link 到新版时，文件的 `upload_version_id` 可仍指旧版，但两版本必须属于同一论文；现有文件服务的版本与权限复核保留。当前 ORM 是 16 张带租户列、12 张不带；T06-7 后会变成 17/11，总数仍是 28。学生/导师发布前的 `result_summaries` SELECT 只经本人 `theses.stage='COMPLETED'`，不反查 `result_publications`；publication SELECT 由 summary 向论文单向追溯。学校 `publish()` 在同一事务把论文置 COMPLETED 并插入 publication；summary 在 COMPLETED 后不可 UPDATE，以免已发布任务集合漂移。学生/导师的 `review_result_versions` SELECT 只从本人可见的已发布 summary 的 `result_task_ids` 和 `is_current` 正式结果放行，不读取 `expert_tasks`；发布前的学校校验仍核对任务归属、轮次和分数，发布后读取还须核对结果数量与 summary 分数一致。专家不能读 `student_eligibilities`，系统管理员不能读 `theses`；`idempotency_keys` 仅本人 SELECT/INSERT。`audit_events` 对业务账号仅 INSERT 本人事件；`actor_id IS NULL` 且 `tenant_id IS NULL` 的文件拒绝事件由认证账号限动作插入，业务账号不读审计全表。

写策略的 `USING/WITH CHECK` 父行引用按以下方向展开：身份成员写入→`organizations`/`tenants`，资格→`tenant_user_memberships`/`review_batches`，论文→`tenant_user_memberships`/`review_batches`，版本→`theses`，轮次→`theses`/`thesis_versions`，任务→`experts`（**不查 `review_rounds`**，以复合外键验证父关系），文件新上传/已归属更新→`thesis_versions`，link→`thesis_versions`（**不查 `file_objects`**，以两个复合外键验证同论文/租户/purpose），草稿/正式评阅→`expert_tasks`，汇总→`theses`/`review_rounds`，发布→`result_summaries`，异议/流程记录→`theses`。`file_objects` 另有删稿解除归属的 UPDATE 例外：旧行限本人上传，更新后 `upload_version_id` 与 `thesis_id` 必须同时为 NULL；已有 link 由复合外键拒绝，service 在解除 link 后执行此操作。此分支不要求新行能查到版本，否则现有删稿会被 RLS 拒绝。这些是**按命令分别适用**的引用；写策略经父表的 SELECT 策略也可能递归，因此不仅要核对上表 SELECT 图，还要核对每条写入引用的传递闭包。每次完成一项迁移后用真实非 owner 连接执行涉及双方的 SELECT/INSERT/UPDATE，捕获 `42P17` 递归错误；不能用 `SECURITY DEFINER` 或宽泛放行解环。跨表子查询仍按调用账号权限执行，需连同关联表 SELECT 权限及 RLS 测试；它们在并发状态变更时也可能读到旧关系，原有 User→AuthSession、批次→membership→eligibility、论文→任务锁和服务层最终复核仍必需。[PostgreSQL 16 策略与并发说明](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)。

外键和唯一约束的内部检查可以绕过 RLS，所以跨校 `tenant_id` 与父 ID 的不一致必须由 `WITH CHECK`、必要时复合外键或约束阻止，并对冲突错误保持无敏感信息的 API 响应。[PostgreSQL 16 行安全说明](https://www.postgresql.org/docs/16/ddl-rowsecurity.html)。避免策略自查询的关系采用复合外键：`organizations(parent_id,tenant_id)→organizations(id,tenant_id)`、`theses(current_version_id,id,tenant_id)→thesis_versions(id,thesis_id,tenant_id)`、`thesis_versions(thesis_id,tenant_id)→theses(id,tenant_id)`、`review_rounds(thesis_id,tenant_id)→theses(id,tenant_id)`、`review_rounds(thesis_version_id,thesis_id,tenant_id)→thesis_versions(id,thesis_id,tenant_id)`、`expert_tasks(round_id,thesis_id,tenant_id)→review_rounds(id,thesis_id,tenant_id)`、`expert_tasks(replaces_task_id,round_id,tenant_id)→expert_tasks(id,round_id,tenant_id)`、`file_objects(thesis_id,tenant_id)→theses(id,tenant_id)`、`file_objects(upload_version_id,thesis_id,tenant_id)→thesis_versions(id,thesis_id,tenant_id)`，以及 T06-7 的 `thesis_version_files(thesis_version_id,thesis_id,tenant_id)→thesis_versions(id,thesis_id,tenant_id)`、`thesis_version_files(file_id,thesis_id,tenant_id,purpose)→file_objects(id,thesis_id,tenant_id,purpose)`。被引用组合须先建 UNIQUE；可空 ID 沿用 PostgreSQL 默认 MATCH SIMPLE，旧数据需先审计，不自动修复。旧 `file_objects.thesis_id=NULL` 的孤儿行只为保留数据，其新 link 因非空论文键而不能引用。T06-4 负责组织自引用约束，T06-5 负责论文、任务与文件约束及任务/文件所属论文回填，T06-7 负责 link 的论文/租户回填和两个复合外键；测试同时覆盖 A/B 父 ID 混搭、同校跨论文、purpose 混搭、草稿复制 link 和原有升降级。`result_summaries.result_task_ids` 是 JSONB ID 集合，不能靠 FK 检查；现有发布集合校验仍需保持。[PostgreSQL 16 复合外键说明](https://www.postgresql.org/docs/16/ddl-constraints.html)。

## 负向验收与回滚

只在 `127.0.0.1:5433/paper_review_test` 的唯一迁移 schema 运行。迁移后用**实际普通账号的新连接**查询 `pg_roles.rolsuper=false`、`rolbypassrls=false`、受保护表 `relowner <> 当前账号 OID`、`relrowsecurity=true`、`relforcerowsecurity=true`，并核对无 owner/认证角色成员关系、无 `TRUNCATE`/`REFERENCES`/schema `CREATE` 权限；查 `pg_policies` 与 28 表清单逐项对账。不能只用 owner、超级用户或 `SET ROLE` 后的单个 ORM fixture 证明 RLS。

| 场景 | SQL 与 HTTP 必须证明 |
|---|---|
| 无上下文/串校 | 普通账号对 `theses`、`file_objects` 和无租户子表读到 0 行；A 学校 session 按 B 的已知 UUID 查询为 0，UPDATE 为 0，INSERT/改写 A→B 父 ID 被拒，包括组织父 ID、论文当前版本、轮次版本、任务论文与替代任务；同校另一论文的匿名 file ID 也不能挂入当前论文 link；API 继续返回既有 404。 |
| 平台/专家 | 平台审核能派 A、B 学校合格论文，但不能读任一原文；专家邀请标题和本人匿名文件按任务阶段可见，`'original'` 不可见，旧任务取消/改派后即使持旧文件 token 也无法读。`tenant_id=NULL` 的平台/专家上下文不能让普通学校 session 跨校。 |
| 管理/结果 | 系统管理员可管理两校元数据和审核账号，对 `theses`、`review_drafts`、`file_objects` 直接查询为 0；专家邀请仍见轮次标题，但直接查 `thesis_versions` 为 0；学生可撤回本人 `CREATED` 轮次；导师/学生发布前看不到结果，发布后仅本人关联结果，直接查 `expert_tasks` 仍为 0，发布后的 summary 不可再改。 |
| 认证/审计 | 登录、refresh 在无业务上下文时照常验证身份；认证账号能读取包括 SUSPENDED 在内租户的 `id/code/status`，但直接查论文被拒；普通业务账号直接 SELECT `users.password_hash` 被拒，学校/系统重置密码和认证登录仍成功；系统 actor 空租户、未认证文件拒绝审计可插入但不能成为全表读取例外；幂等键只能由同一 `user_id` 重放。 |
| 事务/复用 | A 请求 commit、异常 rollback、savepoint rollback 后，在同一池物理连接上以 B/无身份查询，不见 A 行；重新绑定后 B 只见 B 行。运行旧主链全套与隔离浏览器回归。 |

隔离测试 schema、临时角色、存储和端口必须按精确 ID 清理。升级若因策略拒绝现有业务路径，应留在隔离测试库定位缺失的最窄策略，不能用 `USING (true)`、`BYPASSRLS` 或把业务账号改为 owner“修绿”。迁移降级须保留数据，并在隔离环境验证；生产环境不能单独降级到无 RLS 状态作为故障绕行。RLS 上线前还需独立审查策略矩阵、SQL 依赖和权限授予。T07 专家维护、T08 规则快照及 T09–T11 仍由原任务板控制。

## 2026-10-02 已批准的学校终止例外

T11 真实 RLS 浏览器验收发现：学校审核员终止论文时，轮次已取消，但未完成专家任务因原 UPDATE 策略不可写而仍可接受。用户明确批准将权限限为**学校审核员仅能把本校 `INVITED`/`IN_REVIEW` 任务改为 `CANCELLED`**，不授予其他任务编辑权。迁移 `0019_school_task_cancellation` 的策略先按角色、租户和任务状态限制 UPDATE；触发器再核对父论文已 `TERMINATED`、版本只加一，除 `status`/`version`/`updated_at` 外的任务字段不变。父论文检查放在触发器中，以避免任务写策略查询论文、论文读策略查询任务形成 `42P17` 回环。`thesis.service.terminate` 仍按论文→任务顺序加锁。邀请/在评真实非 owner 测试、直接 SQL 负例、迁移升降往返及浏览器终止后的任务/旧文件令牌均已复验；见 [T11记录](../../reviews/2026-10-02-t11-a-browser-validation.md)。上述例外只修订原矩阵的这一个写入动作，其余角色、文件和读取边界不变。
