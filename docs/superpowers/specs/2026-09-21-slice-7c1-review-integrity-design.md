# 7C-1：评阅提交完整性

依据：切片 3/4、2026-09-21 整体审查 A1/A7，用户授权按审查队列继续实施。

## 范围与契约

- 保持现有六维评分、API、单专家与角色权限；不开发更正、多专家、发布快照或页面。
- 同一任务的最终提交和草稿写入取得任务行锁并刷新 ORM 对象，再判断 IN_REVIEW。锁持有到请求事务提交/回滚。
- 最终结果、任务 SUBMITTED、汇总、论文阶段和幂等响应在同一事务内提交。不同 key 或无 key 的第二次最终提交为 409 STATE_TRANSITION_DENIED，不追加或覆盖正式结果。
- 路由在查询幂等缓存前先验证任务所有权并取得同一行锁；同任务相同 key 的并发重试等待首请求事务后再查缓存。
- 幂等摘要包含任务 id 和校验后的全部 ReviewPayload。嵌套字典键序不影响摘要；分数、评语、evaluations 任一内容改变均产生 409 IDEMPOTENCY_CONFLICT。
- 同 key、同内容重试返回原成功数据；无 key 仍允许首次提交。非法分数/缺评语保持 422，不消费 key。
- 已持有旧 IN_REVIEW 对象的请求，在另一个事务提交后不能再保存草稿或最终提交；先写草稿后最终提交则按事务先后正常完成。
- 他人任务保持 RESOURCE_NOT_FOUND；不因命中缓存跳过所有权检查。

## 实现选择与边界

复用 get_task_for_expert，增加可选锁定读取，仅本片写入口及最终提交路由使用；其他读路径不改变。路由对 model_dump 做排序 JSON 序列化后传入现有幂等工具，避免改变其他接口摘要格式。不新增依赖、表或迁移。

旧 submit-final 幂等记录没有请求内容，不能证明重试内容相同；升级后重用旧 key 明确冲突，不推测或回填。既有正式结果不自动纠正。同用户跨不同任务并发复用一个 key 的通用争用不在本片内（key 应按逻辑请求生成）；本片验证同任务相同/不同 key 并发。

## 验收

1. 独立数据库会话预加载旧任务；首提交成功后第二提交/草稿写入明确拒绝，正式结果仅一条 80 分，汇总 80 分。
2. 首事务持锁，第二请求真实等待数据库锁；首事务提交后返回规定的重试/冲突结果。不同 key 最多一次成功，同 key 同内容均返回同一结果。
3. 首事务回滚后另一请求能正常提交，不留下半份结果或汇总。
4. 相同 key 的评分/评语/嵌套评价变化返回冲突；字典键序不同、默认空 evaluations 等语义相同请求可重试。
5. 非本人提交被隐藏，校验失败后可用同 key 修正重试；后端完整测试通过。

使用 5433/paper_review_test、迁移隔离 schema；本片不迁移开发业务库。
