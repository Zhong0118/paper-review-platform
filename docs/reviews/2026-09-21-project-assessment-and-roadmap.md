# 论文盲审平台：现状评估与后续开发路线

评估日期：2026-09-21。代码基线：`codex/frontend-client-demo`，`ee3c3fe`。本文是评估与建议，不替代已生效切片规格，也不表示新增需求已获确认。

## 1. 总体判断

项目已有可复用的业务骨架：真实认证、PostgreSQL 数据模型、论文版本、分层状态、人工派单、评阅结果、发布与异议。适合在现有实现上继续收敛，不需要推倒重建或更换技术栈。

准确阶段是：**单专家垂直切片的开发验证版，正在从演示走向真实业务闭环。** 不能按页面数量判断完成度，也不能把“已有 API”直接理解为“角色可以独立完成工作”。专家真实阅读材料、导师结果入口等仍存在断点，文件与状态约束也有实际缺陷。

本次对照了 CURRENT、README、CONTEXT、六份现行切片规格及相关计划，核对了需求/产品流程、架构安全与历史决策的相关内容，并检查关键前后端服务、路由、迁移和测试。原始材料仅作历史来源核对，未逐页审阅原始 Word/PDF/图片。没有执行完整浏览器 E2E、生产部署、压力测试或迁移恢复验收。

## 2. 项目到底要解决什么

产品是第三方为多所学校提供的送审服务。学校掌握学籍、培养关系、提交资格与结果发布决定；平台组织专家评阅；专家产出独立结果。

| 业务主体 | 负责 | 必须守住的边界 |
|---|---|---|
| 学生 | 本人论文提交、修改、查看已发布结果、异议 | 不能自改学校权威信息，不能识别专家 |
| 学校审核 | 材料与匿名审核、确认送出、进度、发布、异议办结 | 只能处理本校业务，不能识别专家 |
| 百杰审核 | 专家维护、派单、改派、进度与费用运营 | 运营身份可见受授权与审计约束；不能读取原始论文 |
| 专家 | 接拒、阅读匿名材料、评阅 | 接单前不读全文；不见作者、导师或其他专家结果 |
| 导师 | 查看本人指导学生的已发布结果 | 不参与送审前审批，不见专家身份 |
| 系统管理员 | 租户、账号、权限和配置 | 默认没有论文正文和评阅内容读取权 |

历史文档称“五类角色”，现行实现把审核人员拆成学校、百杰两种角色代码，形成六个登录角色。这是概念层级不同，建议统一表述，避免再次引入学院/研究生院等重复角色。

目标业务链：学校身份与资格输入 → 提交原始/匿名文件 → 匿名门禁 → 学校确认送出 → 平台派单 → 专家接拒和评阅 → 异常处理/补审 → 按批次规则汇总 → 学校发布 → 学生/导师查看 → 异议与归档。费用、通知、审计贯穿相关节点。

## 3. 现有成果与边界

| 能力 | 实际已有 | 仍缺或受限 |
|---|---|---|
| 基础工程 | Vue/TS、FastAPI、SQLAlchemy、Alembic、独立 Postgres、健康接口 | 未见仓库 CI 工作流；部署与恢复未验收 |
| 身份权限 | 平台账密、JWT/刷新会话、角色和部分资源关系校验、双租户种子 | 真实租户/账号管理、SSO、权威数据同步、RLS |
| 学生提交 | 草稿、文件上传、提交、退回后新版本、工作流记录 | PDF 真实性、所有权、文件不可变性有缺口 |
| 学校审核 | 通过/退回、确认送出、匿名进度 | 待送审撤回有缺陷；终止尚无完整 API |
| 派单与接拒 | 种子专家、专业匹配、部分回避检查、邀请/接受/拒绝 | 专家库真实维护、完整改派、期限、催审、批次席位约束 |
| 在线评阅 | 真实草稿与最终提交 API、固定六维评分、结果版本表 | 阅读区仍为演示材料；任务选择和字段映射需真实验收 |
| 汇总发布 | 单专家汇总、学校发布、匿名结果详情 API | 人数/规则硬编码；多专家、多轮次、发布快照未完备 |
| 导师结果 | 详情 API 有培养关系授权 | 页面取列表用错学生接口，真实入口不通 |
| 异议 | 提交、受理、结论回填，独立状态，不改原分 | 附件、通知、学校制度配置 |
| 费用/通知/导出 | 前端演示和目录骨架 | 不算真实业务交付 |

当前论文主链为：DRAFT → SUBMITTED → PREPARING → READY_FOR_DISPATCH → UNDER_REVIEW → RESULT_PROCESSING → COMPLETED。确认送出只创建轮次，首个任务创建才进入 UNDER_REVIEW；最终提交与学校发布是不同节点；异议不回退论文阶段。这些分层值得保留。

## 4. 优先处理的实际问题

以下区分定向复现与静态代码证据；未复现并发行为不写成已经发生的事故。

| 优先级 | 问题与影响 | 证据/验证 |
|---|---|---|
| 阻断真实使用 | 提交后仍可 PUT 覆盖已上传文件，审核通过的内容可能被替换 | `backend/app/modules/files/service.py:63` 仅校验上传人；临时 API 探针确认提交后覆盖返回 200 |
| 阻断真实使用 | prepare-upload 校验同租户和草稿，但未校验论文属于该学生 | `files/service.py:27`；服务层探针以同租户、不同用户上下文成功创建上传记录。该探针模拟身份上下文，未声称通过真实账号完成整条攻击链 |
| 阻断真实使用 | 匿名检测未解析 PDF，而是 decode 原始字节；可能漏掉压缩/编码正文，且损坏文件可得 PASS | `thesis/detector.py`；无效 PDF 字节探针返回 PASS。`files/service.py:75` 也缺真实可读性、大小等完整校验 |
| 阻断角色闭环 | 专家评阅工作台仍展示固定摘要、文件名和页数，默认“校验通过” | `frontend/src/modules/review/components/AnonymousDocumentPane.vue`；父页面没有加载真实 materials 的调用 |
| 功能缺陷 | READY_FOR_DISPATCH 返回可撤回动作，实际撤回 409 | `thesis/service.py:125` 与 `workflow/service.py` 不一致；API 探针复现 |
| 功能缺陷 | 导师页面调用学生列表接口，403 被吞成空列表 | `SupervisorResultPage.vue:29`；导师 GET /theses 的 API 探针返回 403；页面还固定显示“建议通过” |
| 规格偏差 | 规格说目标人数来自种子批次，代码却硬编码 REQUIRED_EXPERTS=1，汇总取 totals[0] | `result/service.py:17`、`:58`；当前不能直接通过改常量升级多专家 |
| 规格缺口 | 终止、改派写在规格/枚举中，但没有完整可调用实现 | `dispatch/router.py` 的 task_router 未挂载且无改派处理；学校 router 未见 terminate 接口 |
| 权限规则不一致 | 候选列表考虑 ExpertConflict，真正 assign 未复用该冲突检查 | `dispatch/service.py:71` 与 `:115`；按钮提示不能替代命令端校验 |
| 文件契约不一致 | 下载授权返回 query token，读取接口却只接受 Bearer；标称 5 分钟与通用 access token TTL 也不一致 | `files/service.py:174`、`files/router.py`、`auth/deps.py`、`core/security.py`；需补单对象短期授权与真实浏览器验证 |

还需集中验证：接拒/最终提交并发、幂等键对完整请求内容的绑定、同一轮次重复任务、多个已完成结果的计数、轮次关闭、发布版本固定、退回后复用文件导致多链接查询的问题。现有代码部分使用论文行锁，但不能据此推断所有任务命令已具备并发保护。

## 5. 需要先收敛的业务设计

1. **试点边界与完整 MVP 分开。** 旧 P0 同时包含 SSO、多专家、财务、通知、导出和运维，是较大交付范围。保留为正式产品目标；每轮只选择可验收切片，不能把“延期”误写成“取消”。
2. **一篇论文的四类记录各负其责。** 论文阶段表示宏观位置；论文版本固定材料；轮次组织评阅；任务保存某专家的一次责任。拒绝/改派保留旧任务，修改论文后不能继续引用过期轮次材料。
3. **材料审核必须绑定不可变文件。** PDF 检查、学校通过、派单材料都指向同一论文版本/文件哈希；再次上传必须产生新文件与合适的新版本。
4. **学校规则与评分模板独立于页面。** 目标人数、维度、汇总方式、冲突条件和期限应来自版本化批次规则；启动轮次时固定快照，改配置不改变在途历史。
5. **结果发布固定具体版本。** 专家原始结果、汇总版本、学校发布记录分开；更正必须生成新版本，不能让已发布页面悄悄读取变化中的结果。
6. **异常处理是核心业务。** 拒绝、超时、撤回、终止、延期与更正要明确操作者、允许状态、原因、并发行为以及对材料/结果/费用的影响。
7. **费用遵循独立账本。** 学校额度、冻结/扣减和专家应付/提现不可混成一个余额；计费触发点、取消退费、更正冲正要先约定，再写实现。

不需要通用工作流引擎、微服务或全量重构。继续采用模块化单体，逐片补齐直接影响当前业务的约束。Redis/Celery 随可靠通知和超时任务引入，对象存储随部署准备引入。

## 6. 分阶段路线与验收出口

| 阶段 | 交付重点 | 完成后能做什么 | 验收出口 |
|---|---|---|---|
| A：主链可信 | 修文件授权/锁定/PDF、真实阅文、导师列表、撤回、下载；冻结当前单专家边界 | 用真实 PDF 和虚构身份完整演练 | 多角色 E2E 从提交到发布/异议通过；明确拒绝越权与文件替换 |
| B：脱离种子运营 | 租户/账号最低管理、批次/资格受控输入、专家维护、专业与回避统一校验、规则快照 | 创建新学校、新批次、新学生/专家，不靠改 seed | 两校独立建批次并走业务，不能跨校；在途规则不随配置漂移 |
| C：真实评审调度 | 多专家席位、改派、接单超时、评阅逾期、延期、撤回审批、终止、可靠通知 | 一批论文出现拒绝/超时后仍能推进 | 并发派单不超额，旧任务保留；超时处理和通知可重试且不重复 |
| D：完整结果管理 | 多专家汇总/冲突/补审、更正版本、发布快照、结果/评阅书导出、异议附件 | 不同学校按各自规则返还可信结果 | 不足人数/冲突未处理不可发布；更正不覆盖历史；导出不破盲 |
| E：商业与学校接入 | 学校额度/账单、专家费用与人工付款回填、SSO/学校同步、代传/批量导入 | 支持实际学校运营与收费流程 | 账务幂等可核对；重复/乱序同步不覆盖新数据；批量逐项反馈 |
| F：上线验收 | RLS、私有存储、生产认证配置、审计、备份恢复、监控、迁移/负载测试 | 达到约定试点或上线标准 | 真实双租户隔离、数据库+文件联合恢复、升级路径、关键告警有证据 |

顺序说明：B 的学校数据输入必须经学校授权；SSO/同步接口契约应尽早对齐，实际适配可按试点依赖前移。RLS、审计和备份不是最后才考虑：A 起设计与补测试，**真实数据上线前必须完成 F 的相关门禁**。如果首次试点要求收费或强制 SSO，E 的对应能力必须前移，不能默认豁免。

前端随每片完成真实接线、错误反馈、刷新恢复和必要响应式验收；整体视觉精修在 A/B 稳定后集中做。保留现有可用组件，逐步移除真实路径中的演示依赖，冻结 scenarioService。

## 7. 最近三片建议

### 建议切片 7A：文件安全与匿名门禁

- 先补回归用例：同校他人上传、提交后覆盖、延迟 complete 绑定到错误版本、超限/伪造/加密/损坏 PDF、正文/元数据身份线索。
- prepare/put/complete 统一核验作者、租户、论文版本和可编辑状态；已完成/已提交文件不可原地覆盖。
- 使用真实 PDF 解析；解析失败不能 PASS；扫描件与无法可靠提取文本的文档明确走人工复核或拒绝策略。
- 统一匿名材料访问、短期单对象授权与审计；接单前和非本人任务不可读。
- 出口：在真实 Postgres 与真实 PDF 样例上验证门禁，材料版本在审核/派单/下载之间一致。

### 建议切片 7B：修通真实角色操作

- 接入专家真实匿名 PDF 阅读；以明确 task_id 进入任务，不从列表随意挑第一条。
- 新增导师的受限学生/论文结果列表，区分未发布、无权限与网络错误；删除固定通过结论。
- 修 READY_FOR_DISPATCH 撤回；定义已建未派轮次如何取消，以及新版本再次送审如何产生新轮次。
- 逐项核对 allowed_actions、实际接口、路由入口与状态矩阵；补规格承诺但缺失的必要动作。
- 出口：真实模式下学生→学校→百杰→专家→学校→学生/导师→异议的浏览器全链路，以及退回重提与拒绝再派分支。

### 建议切片 8：批次规则与真实基础数据

- 最小可用的专家档案与状态维护、批次/资格入口、角色分配；只做闭环所需字段。
- 将单专家人数和固定模板迁到有版本的批次配置，轮次创建时保存快照。
- 列表与派单共用回避规则。未支持的规则组合明确拒绝，不默认套用固定分数。
- 在下一片扩展多专家前，完成唯一约束、并发控制和有效结果集合定义。
- 出口：无须修改 seed 即可创建下一批虚构业务，并验证旧轮次不受新规则影响。

7A 与 7B 应先于财务、大屏或更多演示页面。每片继续采用“规格 → 失败测试 → 最小实现 → 集成/角色验收 → CURRENT 更新”的交付方式。

## 8. 测试与工程基线

本次实际执行：

- 后端 `.venv/bin/pytest -q`：**32 passed**，3 条警告。
- 前端 `pnpm test:unit:run`：**50 个文件、361 项测试通过**。
- 前端 `pnpm build`：通过（包含 vue-tsc）；存在包体积和第三方注释警告。
- 额外 5 个临时诊断探针通过：确认同租户不同用户上下文可 prepare-upload、提交后文件可覆盖、待送审撤回 409、导师列表 403、无效 PDF 检测 PASS。这里“通过”表示复现了当前缺陷，**不表示缺陷已修复**。

测试使用本仓库 5433 Postgres、paper_review_test 与临时文件目录；没有执行开发业务库迁移或修改原始材料。临时探针不作为仓库正式回归测试提交。

覆盖不足：前端大量测试面向演示服务；部分 real wiring 测试仅验证手工模拟对象。后端 fixture 使用 metadata.create_all，不能代替 Alembic 从空库/旧版本升级验证。建议增加真正 HTTP+浏览器主链、同校不同学生权限、文件不可变、并发命令、迁移链与双租户隔离测试，然后纳入 CI。

不建议用“393 个测试通过”推导产品已可上线。

## 9. 后续管理方式与待确认事项

- CURRENT 继续作唯一现状入口，补充“已实现但有限制/验收未通过”，避免与代码偏差被遗忘。
- 新路线不重写整个历史文档集；为新切片建立明确需求、数据变更、API、权限与验收。
- 当前分支比本地 main 多 68 个提交。本次不合并。建议 A 验收后收敛成可运行开发基线，再以短分支交付后续切片；main 合并不等于生产上线。
- 先确认首次试点：学校数、论文量、每篇专家人数、是否必须 SSO、是否真实收费、PDF 大小/扫描件比例、实际交付时间与参与人员，再给日历排期。
- 业务规则需学校明确：评分/汇总、冲突阈值、补审、接单/评阅期限、回避范围、更正与再次发布、费用取消退费规则。
- 不擅自增加默认分差、默认异议期限或自动裁定结论。已确认的职责隔离、双盲、版本保留等原则继续执行。
