## 发现与调整

1. **已复现的配置缺口，优先处理。** `backend/app/core/config.py` 的 production 校验仅要求三个不同数据库登录，仍接受默认 JWT 和默认 seed 密码。本轮用 `_env_file=None`、三个虚构 URL 实例化 Settings，无数据库连接，仅输出两个布尔值，均为 True，退出 0。未读取或显示真实密钥。增加生产 fail-closed 配置校验，并阻止演示 seed 在 production 执行，归 T09-A2。
2. **历史实测的日志缺口，优先处理。** T06-8 已记录 Uvicorn 会把测试下载令牌查询串写入访问日志。本轮源码确认验收入口仍用默认 Uvicorn 配置；此轮未重新生成令牌/运行服务。归 T09-A1，修复时必须用真实 server 日志重验，不能只测 formatter。
3. **T07 并发验收错误。** 原计划要求暂停与派单“没有两个成功结果”，与“暂停不撤销已有任务”冲突。正确出口是两种锁先后：暂停先完成则派单拒绝；派单先完成则两者均可成功，既有任务保留，后续派单拒绝。
4. **T07 交付遗漏。** 原只读片提前开放全局账号写权限，前端片未列真实菜单白名单；原降级条件无法可靠识别新增专家。已将写权限和负向测试放回写接口片，补菜单/路由验证，改为仅空专家库允许 downgrade，有数据依赖前向修复或配套恢复。取消“已有独立专家账号恢复流程”的失实表述。
5. **派单目标身份存在待复现缺口。** `dispatch/service.py` 的目标检查有专家服务状态与回避，但未显式检查目标 User.status/有效全局角色；不能只靠目标之后登录时被拒绝。列入 T07-2 先红灯复现再修复。账号停用并发若需要改变锁序必须补设计，尚不宣称已确认或修复所有并发路径。
6. **T08 不应从零做规则平台。** `review/service.py` 已有六维上限，`result/service.py` 已写 `ResultSummary.rule_snapshot`，但人数与汇总来自运行时代码常量。补“轮次创建时固定并供提交/汇总读取”的缺口即可。正式结果等级的枚举映射需先逐项核对，不凭历史文档新造状态。
7. **交付节奏需调整。** 同一功能片定向回归，模块收口再跑全套；功能片带真实页面或明确接口出口，不把每个测试步骤另算任务。T09/T10/T11 拆本地与部署两个阶段，保留原编号，避免没有服务器就全线停工。
