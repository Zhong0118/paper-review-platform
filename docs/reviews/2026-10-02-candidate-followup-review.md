## 已确认问题

### F01 / P1：备份未拒绝跨 schema 依赖，CASCADE 边界可能超出自有资源

位置：[backup_owned_resources](../../backend/scripts/recovery_drill.py:360)、[恢复删除入口](../../backend/scripts/recovery_drill.py:458)。

复现：在本次亲自创建的另一虚构 schema 中建立引用源 `theses` 的 view，再调用备份。预期按 T10 设计拒绝外部依赖，实际成功生成备份，探针报 `DID NOT RAISE ValueError`。当前仅检查归档 TOC 包含源 schema 名称，没有检查数据库依赖关系。

影响：恢复使用 `DROP SCHEMA ... CASCADE`，外部依赖对象也可能被删除，而只导出源 schema 的归档无法恢复外部对象。本轮仅验证备份错误放行，未执行该破坏路径。探针退出前先精确删除自己创建的外部 view 和 schema，再退出源资源上下文。

修复验收：按既有 T10 设计，在备份及进入破坏步骤前拒绝不受支持的跨 schema 依赖，覆盖外部对象依赖源、源对象依赖外部，以及备份后才新增依赖；失败时外部对象和源数据保持完整。允许的系统依赖需明确区分，不可靠 schema 前缀或 TOC 子串判定安全，也不能通过扩大删除授权解决。若恢复资源边界需要变更，先交回复核。

### F02 / P2：清理校验漏掉 schema 所有者变更

位置：[assert_cleanup_stage](../../backend/scripts/recovery_drill.py:104)、[恢复前再次检查](../../backend/scripts/recovery_drill.py:454)。

复现：捕获本次隔离资源所有权记录后，将同一 schema 的 owner 改为测试管理员，再执行 `assert_cleanup_stage('schema')`。预期拒绝，实际通过。OID 在 `ALTER SCHEMA OWNER` 后不变，清理校验只比较 OID；最初 capture 检查的 nspowner 没有持续复核。

影响：资源所有者已经变化，脚本仍把它当作可清理资源，与精确所有权门禁不一致。该问题需要发生所有权变化才触发，不代表日常业务请求可以任意删除 schema。本轮在 finally 中核对 OID 并恢复原 owner 后才退出资源上下文，没有在变更 owner 状态下执行删除。

修复验收：破坏前同时核对 schema OID、当前 nspowner 与本次捕获的角色 OID；身份改变时停止后续清理。覆盖 owner 变化、同名不同 OID、正常自有资源路径，保持原有文件 inode、角色属性和数据库地址门禁。

### F03 / P2：专家回避变更缺少审计摘要

位置：[expert.change](../../backend/app/modules/expert/service.py:73)。

复现：通过真实 HTTP API 给虚构专家新增一条导师姓名回避，再将集合清空，两次均返回 200。读取对应审计，detail 只有 `{'version': 2}`、`{'version': 3}`。旧回避记录被删除，无法从审计判断此次添加还是移除了哪类回避。

影响：未满足 T07 的“审计记录变更摘要，不写敏感全文”约定。代码中资格/服务状态命令也只记录 version，虽然请求要求理由，理由没有保留下来；本轮失败探针直接覆盖的是回避变更。

修复验收：补充符合既有隐私约束的前后变化摘要，并明确理由的安全留存方式；不能把导师姓名、密码或其他敏感全文直接写入审计。覆盖新增/移除/替换/去重、失败回滚、版本冲突不重复产生成功审计。将探针的宽泛存在性断言换成正式字段契约断言；具体摘要若不能由现行设计确定，应先细化该小项契约。
