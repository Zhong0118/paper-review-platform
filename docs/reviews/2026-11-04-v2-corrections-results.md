# BUG-09 与 BUG-04：更正草稿、公开修改建议

基线 `3f40424`。复测使用 `5433/paper_review_test` 的临时 schema 和临时文件，Chrome 直连本次验收的正式模式前端与受限业务 API（15249 / 18249）。下列文本、分数均为测试数据。未更改开发数据库、生产数据或既有发布行。

## BUG-09：更正草稿在失败后消失

**复现。** 在状态为 APPROVED 的更正申请中修改分数、分项评价、总体评价、主要问题、修改建议等字段。修复前，保存返回 500、超时或 409 后，表单随错误分支卸载，修改建议输入框不存在；请求未结束时切换任务还会把前一个任务的“保存中”带到新任务。

**编辑契约。** 当前身份、任务和申请共同限定一份内存中的编辑副本。字段编辑只更新本地副本，必须手动保存；编辑使旧检查确认失效。加载或写入出错时错误信息与表单同时显示。可重试的相同命令复用幂等键。409 不自动重放：先读服务器版本，再展示服务器和本地字段的差异；专家可保留本地继续编辑或使用服务器草稿，前者仍需手动保存。刷新失败保留输入并阻止向未知版本写入。离开该身份、任务或记录清除副本；过期响应不能回填。请求不再获准，或丢失访问权限，停止编辑与重试。

**实测。** Chrome 在更正草稿保存时注入一次 500；以同一专家在另一写入路径合法保存服务器版本 3，原页面继续保存收到真实 409。分数 13、分项评价、优点、总体评价、主要问题、修改建议均保留；服务器新建议和本地建议可分别核对。选择保留本地内容不发送请求，手动保存成功后才继续提交。Vitest 还覆盖 GET 刷新失败、写入超时、提交失败、选择服务器副本、终态、403 和快速切换身份/任务。

证据：[Chrome 版本对照](evidence/2026-11-04-v2/correction-compare.png)；[真实 Chrome 操作](evidence/2026-11-04-v2/correction_browser.cjs)；[回归断言](../../frontend/src/modules/result/__tests__/realCorrections.spec.ts)。

## BUG-04 / C-RESULT：可公开的修改建议

**复现。** 基线的专家意见含 `revisionAdvice`，匿名投影却没有对应字段。三端页面只展示总体评价；即使给页面返回新字段，测试行文本仍只有“E-001、69、不通过、需要重做实验”。五个数据库验收用例在旧发布格式上缺少新字段/模式标记。仅修改应用后再测，原数据库触发器拒绝首次发布：`publication snapshot does not match effective result`。因此需要 `0034_public_revision_advice`，只替换新行的校验函数；保留严格相等、版本链、租户和来源核对以及既有不可变约束。

**公开字段。** 新发布快照标记 `snapshot_schema_version: 2`，在原有匿名别名、总分、六维分数、评审结论、总体评价、主要问题之外，仅新增 `revision_advice`（来源：正式意见的 `revisionAdvice`）。不公开优点、各维文字评价、专家身份、更正私有理由、原文或检查原文。学校审核用的匿名检查摘要不复制进公开条目。无模式标记的已发布行是 v1；响应说明模式为 1，条目仍没有建议字段，页面和 PDF 说明“该发布版本未收录修改建议”。不把今天专家意见中的建议填入历史版本。

**版本和路径。** 实际断言的脱敏摘录如下，只列与契约有关的字段。发布序号（单篇论文第几次发布）与内容模式（该次发布收录哪些字段）是两个概念。

| 场景 | 学校、生效结果与实际导出 |
| --- | --- |
| 首发前学校预览 → 首发 | 测试提交正式意见后学校预览为模式 2、`E-001`、“补充对照”；初次发布写入同一建议。 |
| 已发布、专家提交更正，但学校未确认 | 首条快照仍为 `{"snapshot_schema_version":2,"total":80,"items":[{"alias":"E-001","revision_advice":"补充对照"}]}`（节选）。学生、导师保持原值；学生响应 `correction_pending:true`；学校 PDF 仍为发布版本 1。 |
| COMPLETED 后学校确认更正 | 同一事务追加第 2 条发布记录。受限 API 测试读到 `{"snapshot_schema_version":2,"total":90,"items":[{"alias":"E-001","revision_advice":"请补充样本规模的对照表"}]}`（节选）；学校、学生、导师和 v2 PDF 一致。第一条快照仍为 80 分及原建议。没有二次发布按钮或额外发布动作。 |
| 首发前确认更正 | 学校预览立即反映 90 分和更正建议；随后正常首次发布，由学生读取对应意见，无需先发布旧版。 |
| 平台驳回 / 学校不予确认 | 两种情形均保持旧结果 80 分、“补充对照”，`correction_pending:false`；待确认内容不会成为学生意见。 |
| 旧快照 | 在真实 0033 触发器下写入旧格式，随后升级 0034。升级前后的 `snapshot::text` 完全相同；底层专家原意见确有“补充对照”，学校、学生、导师和 PDF 都没有将它补进旧记录。 |
| 数据库伪造尝试 | 使用受限学校角色向合法的首发请求夹带 `strengths` 或篡改 `revision_advice`；两次均由内容触发器拒绝，SQLSTATE 42501。回滚后正常请求可发布。 |

独立的 Chrome 复测将选题评分从 12 改为 13，因此该次更正结果为 **81** 分，与上表另外一组数据库测试的 90 分不同。实际学生页面和下载的第 2 版 PDF 均出现新建议。检查了 PDF 抽取文本、元数据及渲染页面，未见测试所用的私有理由、优点、分项文字或身份标记。

## 验证范围

两个前端测试文件共 38 项通过；后端聚焦的 7 项通过，覆盖首次/更正/驳回/前后发布、历史迁移、伪造内容拒绝。Vue 类型检查通过。Google Chrome 验收使用本机安装的 Chrome、Playwright、正式模式 Vite 和真实本地受限 API；只对一次保存的 500 做故障注入，409、后续保存、确认更新和文件导出均来自真实服务器。没有模拟浏览器离线恢复、未承诺跨浏览器重启恢复尚未保存的更正文本。
