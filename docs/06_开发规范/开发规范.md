# 开发规范

## 1. 适用范围

本文仅定义未来进入编码阶段后的工程规则，不代表当前已经获得编码授权。只有文档完成一致性审查、编码准入通过、实施计划获确认，且用户明确回复“批准进入编码阶段”后，才可编写业务代码。

## 2. 总体原则

- 采用模块化单体，模块通过应用服务接口协作，不直接访问其他模块私有表。
- 服务端是权限、状态、金额和文件访问规则的最终执行者。
- 每个状态变化必须校验、持久化和审计；外部副作用必须可重试、可去重。
- 需求、API、表、测试和验收标准同步变更，不允许实现领先于正式文档。
- 一个开发任务对应一个可独立验收目标，避免横跨多个业务闭环的大提交。

## 3. 推荐仓库边界

```text
backend/
  app/
    modules/<module>/
      domain/          # 实体、值对象、领域规则
      application/     # 用例、命令、查询和事务边界
      infrastructure/  # 仓储、外部适配器
      api/             # 路由和请求/响应模型
    shared/            # 极少量跨模块基础能力
frontend/
  src/
    modules/<module>/  # 页面、组件、状态与 API 客户端
    shared/            # 设计系统和通用基础设施
tests/
  unit/
  integration/
  contract/
  e2e/
```

实际目录调整必须在实施计划中列明。不得仅为追求形式一次性搬迁或生成完整脚手架。

## 4. 后端规范

### 4.1 分层职责

- API 层：认证上下文、输入解析、调用用例、输出投影；不得包含核心业务判断。
- 应用层：组织用例、事务、幂等、审计与跨模块接口调用。
- 领域层：状态机、规则快照、评分计算、权限不变量；不得依赖 Web 框架。
- 基础设施层：SQLAlchemy 仓储、对象存储、Redis/Celery 和外部系统适配器。

### 4.2 Python 与类型

- 使用明确类型注解；公共接口、领域命令和持久化模型不得依赖隐式字典结构。
- Pydantic 请求模型与 SQLAlchemy 持久化模型分离，避免把数据库字段直接暴露为 API。
- 时间使用带时区对象；金额使用整数最小单位或 `Decimal`。
- 枚举集中定义并由状态机、API 和数据库约束共同引用。
- 异常转换为稳定业务错误码，不向客户端泄露内部异常。

### 4.3 数据访问

- 每次租户业务查询都必须具有可信租户上下文；禁止以客户端参数代替安全上下文。
- 仓储接口默认限定租户；跨租户平台任务使用专用接口、主体和审计。
- 查询需避免 N+1；新增高频列表在合并前检查查询计划或等价证据。
- 数据结构变化全部使用 Alembic 迁移；迁移需说明向前、回滚或兼容策略。

### 4.4 事务、任务和集成

- 状态变化、事件记录和任务投递意图处于同一事务边界。
- Celery 任务至少一次执行，处理器必须幂等；重试采用有限退避并区分可重试错误。
- 外部适配器具有超时、熔断或失败降级、签名验证、重放保护和可观测性。
- 不以空函数、永久 TODO 或吞异常模拟尚未确定的外部能力。

## 5. 前端规范

- Vue 3 统一使用 TypeScript 和 Composition API；页面按业务模块组织。
- Element Plus 作为基础组件库，视觉和交互通过项目级设计令牌统一，禁止页面各自定义相近组件。
- 路由守卫只改善体验，不能替代服务端授权。
- API 类型从确认的 OpenAPI 契约生成或严格同步；不得长期维护相互漂移的手写副本。
- 表单必须显示字段级错误、状态冲突和可恢复操作；最终提交、撤回、发布、改派和付款回填需二次确认。
- 上传显示进度、类型/大小校验、失败重试和匿名检查结果；不得在浏览器持久化签名地址或敏感论文内容。
- 可访问性基线包括键盘操作、可见焦点、语义标签、错误提示关联和足够颜色对比。

## 6. API 与安全规范

- 新增接口必须具有 API 编号、权限规则、数据投影、错误码、幂等与审计说明。
- 对象级权限在查询前或同一受控查询中验证，禁止“先查全量再前端过滤”。
- 日志、追踪和错误报告不得包含令牌、完整论文、完整评语、对象键、签名 URL 或身份映射。
- 密钥只来自受控配置或密钥管理系统；仓库、镜像和前端包不得包含生产密钥。
- 文件类型不得只信任扩展名；上传后检查摘要、内容类型、恶意文件和匿名规则。
- 依赖版本需锁定；引入新业务依赖必须在实施计划中说明用途、维护性、许可证和替代方案。

## 7. 命名、文档和提交

- 代码使用一致英文领域术语，中文产品名称在文档和界面中维护映射。
- 数据库表和字段使用 `snake_case`；API 资源使用复数名词，业务动作使用 `:verb` 或明确子资源并保持一致。
- 注释解释原因和不变量，不重复代码表面行为。
- 每次需求变化同步对应正式文档和追踪矩阵；未经确认不得将文档标记 `APPROVED`。
- 提交范围保持单一目标，不混入格式化整个仓库或无关重构。

## 8. 测试要求

- 领域规则和状态机先写单元测试；仓储、RLS、对象授权和事务写集成测试；API 写契约测试；关键闭环写端到端测试。
- 修复缺陷必须先增加能够复现的测试，再修复。
- 所有权限变更必须增加允许与拒绝两类测试，尤其覆盖跨租户和盲审身份泄露。
- 时间、超时和异步任务使用可控时钟与可替换适配器，不依赖真实等待或生产外部系统。
- 测试数据不得使用真实学生、专家、论文或支付信息。

## 9. 合并质量门禁

未来每个实现任务至少满足：

1. 对应需求与验收编号明确；
2. 代码格式、静态检查和类型检查通过；
3. 相关单元、集成、契约和端到端测试通过；
4. 数据迁移完成向前与兼容性验证；
5. 权限、租户、盲审、幂等、并发和审计检查通过；
6. API、数据库、运维和用户文档同步；
7. 不包含密钥、真实数据、空实现或未追踪业务规则；
8. 回滚或安全关闭方式清晰。

## 10. Definition of Done

一个功能只有在实现、测试、可观测、可运维、文档和验收证据齐全后才算完成。页面可点击、接口返回成功或单元测试通过，均不能单独代表业务功能完成。
