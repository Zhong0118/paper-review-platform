# 测试与验收

## 1. 目标

测试必须证明平台既能完成 P0 最小业务闭环，也能守住多租户和双向盲审边界。所有 P0 需求必须至少具有正常流程、异常流程和越权流程；状态命令还需覆盖重复请求和并发冲突。

## 2. 测试分层

| 层级 | 重点 | 运行时机 |
|---|---|---|
| 单元测试 | 状态机、匿名规则、评分/冲突、费用、权限不变量 | 每次提交 |
| 集成测试 | PostgreSQL/RLS、仓储、事务、对象存储、Redis/Celery 适配 | 每次合并 |
| API 契约测试 | 请求响应、错误码、投影、幂等、并发 | 每次合并 |
| 端到端测试 | 五角色关键闭环和异常恢复 | 候选版本 |
| 安全测试 | 跨租户、越权、身份泄露、文件授权、日志脱敏 | 每次候选版本 |
| 运维演练 | 备份恢复、任务重试、告警、回滚 | 上线前及制度化周期 |

## 3. P0 验收标准

### 3.1 租户、身份和角色

| 编号 | 验收标准 |
|---|---|
| AC-001 | 学校 A 的任一普通或审核账户无法通过列表、ID 猜测、导出、文件地址或搜索访问学校 B 数据。 |
| AC-002 | 学校系统同步的身份、组织、批次和资格可被平台使用；学生不能修改权威字段，源系统更正后可安全重放同步。 |
| AC-003 | 系统仅采用五类核心角色；每个角色的菜单、API、对象和组织范围与权限矩阵一致。 |
| AC-004 | 系统管理员默认不能读取论文正文、评语或作者—专家映射，紧急访问必须通过授权和审计。 |

### 3.2 提交、匿名与撤回

| 编号 | 验收标准 |
|---|---|
| AC-005 | 有资格学生可保存草稿、上传原件和匿名件、提交；无资格、缺文件或校验失败时不能提交。 |
| AC-006 | 匿名件中的姓名、学号、导师、致谢、文件名或元数据命中规则时阻塞送审，并给出不泄露额外信息的定位提示。 |
| AC-007 | 原件和匿名件独立存储与授权；专家永远不能下载原件；学校侧审核人员不能获知专家身份；百杰运营侧为派单/进度/费用可见学生与专家身份，但原始版默认不向其开放。 |
| AC-008 | 送审前撤回可返回草稿并保留版本；送审后申请经学校审核，取消未完成任务、排除已交结果但保留历史，然后返回草稿。 |
| AC-009 | 仅学校审核人员可因确认的严重原因永久终止；终止不可恢复，理由和操作完整留痕。 |

### 3.3 专家、送审和任务

| 编号 | 验收标准 |
|---|---|
| AC-010 | 平台共享专家可服务多个学校，但学校之间无法看到专家在其他学校的任务和使用信息。 |
| AC-011 | 学校审核人员确认匿名材料后，百杰审核人员可在不泄露专家给学生/导师的前提下，按送审专业方向、专家擅长领域和回避规则人工选择专家。 |
| AC-012 | 专家接受前只见匿名概要、学科、期限和说明；显式接受后才可访问完整匿名材料；拒绝必须填原因。 |
| AC-013 | 接受超时自动关闭邀请并通知人工改派；评阅超期保留草稿和任务，由审核人员催审、延期或取消改派。 |
| AC-014 | 改派关闭原任务并在同一轮次新建任务；新论文版本或正式复核新建轮次，历史链可追溯。 |
| AC-015 | 两名审核人员并发指派、改派或补审时，不会产生超出规则的重复有效任务；冲突请求得到明确反馈。 |

### 3.4 评阅、汇总、发布与异议

| 编号 | 验收标准 |
|---|---|
| AC-016 | 专家可保存草稿；最终提交按模板评分模式（分项平均或总分+评语）校验并锁定；重复提交不产生重复结果；获批更正产生新版本且保留旧版本。 |
| AC-017 | 每名专家的分项、总分和评语独立保存；任何审核人员均不能修改原始结果。 |
| AC-018 | 使用批次规则快照计算汇总和冲突；无规则时只展示独立结果，不生成推测结论；分项平均与总分两种模式均保留各专家原始结果。 |
| AC-019 | 冲突只触发标记和同轮补审；补审结果纳入有效集合后重新生成汇总版本，不覆盖旧汇总。 |
| AC-020 | 只有学校审核人员确认发布后，学生和导师才看到每位专家分数、可发布评语及汇总，且看不到专家身份。 |
| AC-021 | 学生可提交异议理由和附件；平台可提醒、记录线上或学校线下处理方式、状态和结论，并保留审计。 |

### 3.5 费用、通知、审计、导出和恢复

| 编号 | 验收标准 |
|---|---|
| AC-022 | 有效评阅按规则生成费用和余额流水；重复任务不会重复入账，冲正不修改历史流水。 |
| AC-023 | 专家可在线申请提现；授权人员可人工审核并回填线下支付信息，余额、冻结和支付状态一致。 |
| AC-024 | 关键业务事件产生站内通知及一个配置的外部渠道记录；失败可重试且不会重复轰炸。 |
| AC-025 | 登录、权限、同步、下载、状态、指派、评阅、发布、异议和财务操作均可按权限审计，日志不含敏感正文或密钥。 |
| AC-026 | 评阅书和基础统计导出遵循当前角色数据范围；下载地址短时有效，临时文件 7 天后失效。 |
| AC-027 | 每日数据库和文件备份至少保留最近 7 个恢复点；上线前能从同一恢复点恢复数据库与对象并验证关键关联。 |
| AC-028 | 学生不出现支付入口；学校确认送审时按规则快照冻结额度，额度不足不创建任务；有效评阅后学校账单转已消费且专家收入只入账一次。 |

## 5. 必测状态与权限组合

每条状态迁移至少测试：合法角色成功、其他四类角色拒绝、错误租户拒绝、错误前置状态拒绝、重复请求幂等、并发版本冲突、审计事件存在。涉及盲审的响应再进行敏感字段快照检查，确保序列化结果中不存在被排除身份。

## 6. 测试数据和环境

- 至少准备两个学校租户、不同组织、多个学生、导师和共享专家，用于真实隔离测试。
- 使用完全虚构姓名、论文、联系方式、支付和资质信息。
- 测试环境的 PostgreSQL RLS、对象存储私有策略、Redis/Celery 行为必须与生产配置同构。
- 外部学校系统和通知渠道使用契约桩，支持超时、重复、乱序、签名错误和部分失败。
- 时间相关测试使用可控时钟，禁止以长时间休眠验证超时。

## 7. 非功能验收基线

- NFR-005 的 P95 1 秒/3 秒是草案响应目标，不包含未定义的并发和数据规模承诺；编码前必须完成用户量、文件量和峰值任务量估算并冻结测试负载。
- 常用列表、详情和命令应在冻结的负载条件下验证；大文件上传、导出和通知使用异步进度，不阻塞请求线程。
- 候选版本执行依赖、静态、安全头、文件上传、对象授权和常见 Web 风险检查。
- 无障碍和浏览器兼容基线在 UI 实施计划中确定并进入验收，不得仅靠人工主观判断。

## 8. 发布准入

候选版本只有在 P0 AC 全部有证据、关键 TC 全部通过、无未接受的 P0/P1 安全缺陷、联合恢复演练成功、回滚方案验证、配置和密钥检查通过后才可发布。任何豁免必须记录责任人、影响、时限和补救计划。
